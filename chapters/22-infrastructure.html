Chapter 22

Infrastructure: virtualisation, containers, backup

The supervisory layer of a modern BMS is software. That software runs on hardware, inside virtual machines or containers, and it must survive disk failures, bad updates and ransomware. This chapter covers the platform under the BMS and how to get it back when it breaks.

22.1 Hypervisors: ESXi, Proxmox

A hypervisor lets one physical machine run several isolated operating systems, called virtual machines (VMs). Each VM believes it has its own CPU, RAM, disk and network cards. The hypervisor shares the real hardware between them and keeps them apart.

For a BMS this is useful for three reasons. First, consolidation: the BMS server, a historian database, a VPN gateway and a test instance can share one well-built host instead of four small boxes. Second, isolation: a crash or a bad update inside one VM does not touch the others. Third, and most important, snapshots and whole-machine backups: a VM is just a few files, so it can be copied, rolled back and restored onto different hardware.

Type 1 and type 2

A type 1 (bare-metal) hypervisor is the operating system of the host. It boots directly on the hardware. VMware ESXi, Proxmox VE (KVM on Debian Linux), Microsoft Hyper-V and XCP-ng are type 1. A type 2 (hosted) hypervisor is an application on a normal desktop OS: VirtualBox, VMware Workstation, Parallels. Type 2 is fine for a laptop lab. It is wrong for production, because the VM now depends on a desktop OS that reboots for updates, sleeps and runs other software.

Sizing a host

A supervisory BMS is light on CPU and heavy on reliability. A typical small site might run a BMS VM with 2 vCPU and 4–8 GB RAM, a time-series database with 2 vCPU and 4 GB, and a few utility VMs. A 6-core host with 32 GB RAM and mirrored NVMe disks has plenty of headroom. CPU can be overcommitted (more vCPUs than physical cores) because most VMs are idle most of the time. RAM should not be overcommitted on a small host: when the host runs out, it swaps or kills VMs, and you lose the most important one first.

Give a VM the vCPUs it needs, not the most you can. A VM with 8 vCPUs on a 6-core host can wait longer to be scheduled than one with 2, because the hypervisor has to find free cores for it. Start small and grow from measured load.

Snapshots

A snapshot freezes a VM's disk at a point in time. New writes go to a delta file. Rolling back throws the delta away. Snapshots are perfect before an upgrade: take one, upgrade, test, then delete it. They are not backups. They live on the same storage as the VM, so a failed disk takes both. On VMware, long-lived snapshots also grow without limit and slow the VM down.

An integrator runs a BMS server, an InfluxDB historian and a WireGuard VPN as three VMs on one fanless mini PC with Proxmox VE. Before every BMS upgrade the technician takes a snapshot. When an upgrade breaks a driver, rollback takes under a minute. Nightly backups go to a separate backup server, not to the snapshot.

Why is a type 2 hypervisor a poor choice for a production BMS server?

  • Type 1 runs on bare metal. Use it for production. Type 2 is for labs.
  • Overcommit CPU carefully. Do not overcommit RAM on small hosts.
  • A snapshot is a rollback point, not a backup.

22.2 Virtual NICs and multi-network VMs

A VM has virtual NICs. Each one plugs into a virtual switch inside the host. The virtual switch is connected to one or more physical NICs, called uplinks. With VLANs, one physical cable can carry several networks, and each VM NIC can be placed on exactly the network it needs.

A BMS server is often multi-homed. It needs the office or management LAN for operators, the OT network for BACnet and Modbus devices, and maybe a separate VLAN for AV or audio. Giving it one virtual NIC per network keeps the networks separate at layer 2 and makes the firewall rules explicit.

Emulated vs paravirtual NICs

An emulated NIC pretends to be a real, well-known chip, such as an Intel E1000. Every guest has a driver, but each packet costs extra work because the hypervisor imitates hardware registers. A paravirtual NIC (VMXNET3, virtio) is designed for VMs. The guest needs a driver, which modern Linux has built in, and in return gets far lower CPU use and higher throughput. Use paravirtual NICs by default. Fall back to emulated ones only for installers or old guests without drivers.

High packet rates (multicast audio, PTP-timed media streams, busy BACnet broadcast domains) are where emulated NICs struggle first. If a VM shows drops or timing errors under multicast load, switching to a paravirtual NIC is one of the first things to try.

Trace the path

Inside the guest, a VM NIC on a port group with a VLAN ID sees plain untagged frames. The tagging and untagging happen in the virtual switch. This is the most common setup. The alternative, VLAN trunking into the guest (VMware VLAN 4095, or an untagged bridge in Proxmox with VLAN interfaces inside the guest), is useful for routers and firewalls but adds configuration inside the VM.

Rules for a multi-homed VM

  • Only one NIC gets a default gateway. The others get addresses without a gateway, plus specific routes if needed. Two default gateways cause asymmetric routing that is hard to debug.
  • Do not let the VM route between its networks. Disable IP forwarding unless it is meant to be a router.
  • Fix MAC addresses for NICs used by licences or DHCP reservations. Some platforms regenerate MACs when a VM is cloned or restored.
  • Map NICs by MAC, not by order. After a restore or hardware change, guest names like eth1 or ens19 can swap.
  • For latency-critical media networks, consider a dedicated physical NIC, or PCI passthrough so the guest owns the hardware. Passthrough blocks live migration and some snapshot types.
A BMS VM on Proxmox has net0 on vmbr0 with tag 10 for the office, net1 on vmbr0 tag 20 for BACnet/IP controllers, and net2 on vmbr1, a bridge bound to a second physical NIC that connects only to an audio network switch. All three are virtio. Only net0 has a gateway.

A VM NIC sits on a port group with VLAN ID 20. What does the guest OS see?

  • VM NIC → port group/VLAN → virtual switch → physical uplink → physical switch port.
  • Use paravirtual NICs (VMXNET3, virtio) by default.
  • One default gateway per VM. Map NICs by MAC.

22.3 Docker and containers

A container is a group of processes that the host kernel isolates. Linux namespaces give it its own view of process IDs, network interfaces, mount points and hostnames. cgroups limit its CPU and memory. The container shares the host kernel. There is no guest OS to boot, so a container starts in a second and costs megabytes, not gigabytes.

Images, containers, volumes

TermWhat it is

ContainerA running instance of an image, with a thin writable layer on top. Delete the container and that layer is gone.

NetworkBridge (private network with NAT, the default), host (shares the host's stack), macvlan/ipvlan (own address on a physical LAN).

Compose: the whole stack in one file

Docker Compose describes several containers and their volumes and networks in a YAML file. That file is the documentation of your deployment and belongs in version control.

services:
  mqtt:
    image: eclipse-mosquitto:2.0.18   # pin a version, never :latest
    restart: unless-stopped
    ports: ["1883:1883"]
    volumes:
      - ./mosquitto/config:/mosquitto/config
      - mqtt-data:/mosquitto/data
  historian:
    image: influxdb:2.7
    restart: unless-stopped
    volumes: ["influx-data:/var/lib/influxdb2"]
    mem_limit: 2g
volumes:
  mqtt-data:
  influx-data:

Network modes matter for building protocols

The default bridge network uses NAT. That is fine for TCP services like MQTT or HTTP. It breaks protocols that rely on broadcast or multicast: BACnet/IP Who-Is, mDNS discovery, SSDP, and multicast audio streams. For those, use network_mode: host or a macvlan network, so the container sits directly on the LAN.

How much does each model cost?

Containers are not a security boundary as strong as VMs. A container started with --privileged, with the Docker socket mounted, or running as root with host networking can often take over the host. Treat those options as "this container is the host".
A common small-site stack: an MQTT broker, Node-RED for glue logic, a time-series database and Grafana, all in Compose on one Debian VM. An update is docker compose pull && docker compose up -d. A rollback is changing the tag back. The data survives because it lives in named volumes, which the nightly backup copies.

A BACnet/IP gateway in a container cannot discover any devices, but it can reach a device by IP. The container uses the default bridge network. Likely cause?

  • Containers share the host kernel. Light and fast, weaker isolation than VMs.
  • Data lives in volumes. Pin image versions. Keep Compose files in git.
  • Broadcast and multicast protocols need host or macvlan networking.

22.4 Edge hardware: mini PCs, industrial PCs

The edge is the computer that sits in the building, close to the controllers. It might host the whole BMS, or only a gateway that forwards data to a central server. Choosing it is a trade-off between price, lifetime, environment and how easy it is to replace.

What really matters

  • Storage endurance. Databases and logs write all day. A historian writing 5 GB/day uses about 1.8 TB/year. A cheap 256 GB SSD rated 150 TBW lasts decades at that rate, but an SD card does not. Check TBW and prefer drives with power-loss protection.
  • Redundant disks. A ZFS mirror or RAID 1 of two SSDs turns a disk failure from an outage into a maintenance task.
  • Power. DC input that fits the panel's 24 V supply, and a UPS that signals shutdown over USB or network (see chapter 17).
  • NICs. Count networks before buying. Two or more Intel NICs avoid driver trouble with some hypervisors.
  • Out-of-band access. IPMI, iDRAC, iLO or Intel AMT lets you see the console and power-cycle the box remotely. Without it, a hung boot means a site visit.
  • Lifecycle. If the model is discontinued in a year, a spare in five years is a different machine. Virtualisation softens this: the VM moves to new hardware.

Pick a class

A consumer mini PC on top of a hot boiler-room cabinet, with its fan full of dust, is a very common cause of "the BMS was down for three days". Environment ratings are not marketing: check them against the room.

A historian writes 8 GB per day. The SSD is rated 300 TBW. Roughly how long until the rated endurance is used?

  • Match the hardware to the room: temperature, dust, power.
  • Mirror the disks, check TBW, avoid SD cards for databases.
  • Remote console access saves site visits.

22.5 Backup strategy: 3-2-1, offsite

A backup is a copy that survives the event that destroyed the original. Different events destroy different things: a disk failure kills one drive, a fire kills the building, ransomware kills everything it can reach over the network, and an operator mistake kills data that is then faithfully copied to every replica.

The classic rule is 3-2-1: at least 3 copies of the data, on 2 different media or systems, with 1 copy offsite. A modern extension is 3-2-1-1-0: plus 1 copy that is offline or immutable, and 0 errors when restores are tested.

What to back up

ItemWhyHow
Whole VMsFastest full restoreHypervisor backup (vzdump, Proxmox Backup Server, Veeam)

DatabasesA copied file of a running DB may be inconsistentNative dump or snapshot-aware backup

Secrets and docsRestore is impossible without passwords and licence keysPassword manager with offline export, printed runbook

Build a backup plan

Retention and immutability

Keep many restore points, not just the last one. A common scheme keeps 7 daily, 4 weekly and 12 monthly backups. Ransomware or a silent misconfiguration may sit unnoticed for weeks, and the last good copy may be old. Immutable storage (object lock in S3-compatible storage, append-only backup repositories, rotated offline disks) prevents an attacker with admin rights on the BMS from deleting the backups too.

Encrypt offsite copies, and store the key somewhere that does not depend on the system being restored.

Sync is not backup. RAID is not backup. Replication is not backup. All three copy a deletion or an encryption instantly. They protect availability, not history.
A site backs up its BMS VMs nightly to a Proxmox Backup Server on a separate box in another room, which then syncs to a second backup server at the integrator's office. Every quarter, a USB disk is filled and taken offline. That is four copies, three systems, one offsite, one offline.

Production data on a RAID 1 array, plus a nightly copy to a NAS in the same rack. Does it meet 3-2-1?

  • 3 copies, 2 media or systems, 1 offsite. Add 1 offline/immutable and 0 restore errors.
  • Back up controller programs and network configs, not just servers.
  • Keep history. Snapshots, RAID and sync are not backups.

22.6 Disaster recovery

Backups are the ingredients. Disaster recovery (DR) is the tested procedure that turns them back into a working system. Two numbers define the target:

  • RPO, recovery point objective: how much data you can afford to lose, measured in time. Nightly backups give an RPO of up to 24 hours.
  • RTO, recovery time objective: how long the service may be down before it is back.

For a BMS, the RTO is often set by how long the building can run "headless" on its local controllers. If the controllers keep heating and ventilating on their own (chapter 1), a few hours of supervisory outage is uncomfortable but safe. Trend history has a softer RPO; alarm configuration and programs have a strict one, because redoing a week of engineering work is expensive.

RPO and RTO on a timeline

Runbook

A runbook is a written, step-by-step restore procedure that a competent person who did not build the system can follow at 3 a.m. It lists where backups are, which credentials are needed, the order of restore and how to verify success. Step through a typical one.

Test it, or it does not exist

An untested backup is a hope. Schedule restore tests: at least once a year a full restore onto spare hardware or an isolated network, and more often for single VMs. Time the test, which gives you your real RTO. Many backup tools can verify checksums automatically, but only a real restore proves the application starts.

Restore tests MUST run on an isolated network. A restored BMS that comes up on the live OT network will start writing to real controllers with old setpoints and schedules.
After a disk failure, a facility team restored its BMS VM from the previous night's backup onto a spare mini PC in about 90 minutes. The controllers ran the building the whole time. The only loss was 14 hours of trend data, which was within the agreed 24-hour RPO.

Backups run daily at 02:00. The server dies at 17:00 and is back at 19:30. What were the RPO and RTO achieved?

  • RPO is data loss in time; RTO is downtime.
  • Write a runbook someone else can follow, and keep it outside the system.
  • Test restores on an isolated network and time them.
