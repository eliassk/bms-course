Chapter 20

Building a custom BMS front end

Sometimes the vendor dashboard is not enough. This chapter shows how a purpose-built operator interface is put together: the architecture, who may see and do what, how every action is recorded, how it runs on a wall panel for years, and how to design screens that make problems obvious.

20.1 Why build vs. use vendor dashboards

Every BMS platform from Chapter 19 ships with a front end. Niagara has its Px pages and web profiles. Desigo CC, EcoStruxure Building Operation and Metasys have their own workstations and web clients. Home Assistant has Lovelace dashboards. For most buildings, these are the right answer. They are supported, documented and maintained by someone else.

A custom front end is a separate web application. It sits on top of one or more platforms and talks to them through their APIs. It owns no control logic. It is a presentation and workflow layer. You build one when the vendor UI cannot express what the users need, not because you like writing code.

Reason to buildExampleCan the vendor UI do it?
Several platforms, one operatorHVAC in one BMS, lighting in a DALI server, AV in a control processor, meters in a historian.Usually only via integration drivers, often at extra licence cost.
Task-focused screens for non-expertsA venue manager needs "Open the hall for an event" as one button, not 40 points.Possible with scripting, but the page model fights you.
Fine-grained permissionsStage crew may control stage lighting only, during booked hours.Often limited to coarse roles or per-object categories.
Own branding and devicesWall tablets in every room, phone access for staff.Web clients exist but may not suit small touch screens.
Avoid lock-inThe UI survives a change of controller vendor.No, by design.

The costs are real and long-lived. You now own security patches, dependency upgrades, browser changes, accessibility, documentation and on-call support. A rule of thumb from software practice: the first release is perhaps 20–30 % of lifetime cost. The rest is maintenance. A front end in a building may live 10–15 years.

Try it: rough cost comparison

A 3000-seat concert venue runs HVAC on one BMS, house lights on a DALI-2 server, and audio on a DSP platform. The vendor BMS could show the other two only through a costly integration and a page designer. The team builds a small web app with six task screens ("Doors open", "Show", "Interval", "Load-out"). It reads and writes through each system's API and has no logic of its own. Interlocks stay in the controllers.
Do not move control logic into the front end "because it is easier there". A browser tab can close at any time. If heating, ventilation or safety depends on a page being open, the design is wrong.

Which reason is the weakest for building a custom front end?

  • A custom front end is a presentation and workflow layer. Control logic stays in controllers.
  • Build when users need tasks across systems, fine permissions or own devices.
  • Most lifetime cost is maintenance. Budget for it before writing code.

20.2 Architecture: SPA, backend proxy, live data

The common shape has three tiers. A single-page application (SPA) runs in the browser. It is built with a framework such as React, Vue, Svelte or Angular and served as static files. A backend (often called a backend-for-frontend, BFF) runs on a server. The building platforms sit behind it: a BMS REST API, a BACnet/IP gateway, an MQTT broker, a historian.

The browser never talks to the building systems directly. That is the most important rule in this chapter. Platform tokens, controller IPs and write paths stay on the server side. The backend checks every request against the user's permissions, writes the audit record and only then forwards it.

Follow one command

Live data: polling, SSE or WebSocket

Operators expect values to move without pressing reload. There are three ways to get there.

MethodHow it worksTrade-offs
PollingBrowser asks every N seconds.Simple. Latency up to N s. Load grows with clients × points even when nothing changes.
Server-Sent EventsOne long HTTP response streams text events, server to browser.One direction only. Auto-reconnect built in. Works well through proxies.
WebSocket (RFC 6455)HTTP upgrade to a full-duplex frame channel.Lowest latency, both directions. You handle reconnect, heartbeats and resync yourself.

A robust live channel follows a pattern: on connect, the backend sends a snapshot of every entity the user may see. After that it sends only deltas. Each delta carries a sequence number or timestamp. If the browser sees a gap, or the socket drops, it reconnects with exponential backoff (for example 1, 2, 4, 8 s, capped at 30 s, with random jitter) and asks for a fresh snapshot.

// delta message, server to browser
{"type":"delta","seq":48213,"id":"ahu1.supply_temp",
 "value":18.4,"unit":"°C","quality":"good","ts":"2026-03-02T09:14:07Z"}

Note the quality field. A value from a device that went offline must not look like a fresh value. The UI should grey it out or mark it stale (see 20.5).

Exercise: where does it belong?

Frost protection stops the supply fan.
Check whether the user may change this setpoint.
Format 18.437 as "18.4 °C".
Hold the API token for the BMS.
PID loop for supply air temperature.
A campus front end serves about 80 concurrent operator sessions. The backend holds one subscription to the MQTT broker and one to the BMS change-of-value feed. It keeps an in-memory map of about 25 000 entity states and fans deltas out to WebSockets, filtered per user. Peak traffic is a few hundred deltas per second. A single small virtual machine copes.
Do not let each browser open its own MQTT or BACnet connection "to save a hop". You lose central permissions, audit and caching, and the broker's credentials end up in JavaScript any user can read.

A WebSocket reconnects after a 40 s network drop. What should happen first?

  • Browser → backend → platforms. The browser never holds platform credentials.
  • The backend enforces permissions, writes the audit record and caches state.
  • Live data: snapshot on connect, then deltas with sequence numbers. Resync on any gap.

20.3 Authentication and role-based access

Authentication answers "who are you?". Authorisation answers "what may you do?". Keep them separate in code and in your head.

Authentication options

ApproachHowFit
Single sign-on via OpenID ConnectRedirect to the organisation's identity provider (Entra ID, Okta, Keycloak, Authentik…). Authorization code flow with PKCE.Best for staff. Leavers lose access when IT disables their account.
Reverse proxy authenticationA proxy in front (e.g. oauth2-proxy, an ingress with auth) logs the user in and passes a verified identity header.Simple, but the app MUST only accept that header from the proxy.
Local accountsUsername + password stored as a slow hash (Argon2id, bcrypt). Add TOTP or WebAuthn.Small sites without an identity provider.
Device accountsA wall panel gets its own long-lived, revocable credential bound to one role.Kiosks (20.5).

After login, the backend keeps a server-side session and gives the browser a cookie with HttpOnly, Secure and SameSite=Lax or Strict. JavaScript cannot read an HttpOnly cookie, so a cross-site scripting bug cannot simply steal it. Storing access tokens in localStorage is the common anti-pattern. Typical lifetimes: idle timeout 15–60 min for operator sessions, absolute limit 8–12 h, so a shift ends with a fresh login.

Role-based access control

RBAC assigns permissions to roles and roles to users. In a building, a permission is usually an action on a group of entities: view, operate (switch, change a setpoint within limits) and configure (schedules, limits, alarm thresholds). Groups follow systems and areas: "HVAC plant", "Stage lighting", "Meeting rooms floor 2".

Pure RBAC gets coarse fast. Add attributes where needed (this is ABAC): "operate meeting room lights only while the room is booked by you", or "setpoint between 19 and 24 °C". Keep the policy in one place on the server, as data, and test it like code. The UI should hide what a user cannot do, but hiding is only comfort. The server MUST refuse it anyway.

A university gives cleaning staff a "Night round" role. It can view all areas and switch corridor lighting, nothing else. Security guards get view on everything plus operate on doors and lighting. Facility engineers get configure on HVAC. When a contractor joins for a chiller replacement, they get a time-limited HVAC-tech role that expires after four weeks.
The classic RBAC bug is checking the permission in the UI and forgetting it in one backend endpoint. Anyone with the browser's developer tools can call that endpoint. Write a test that calls every write endpoint as every role.

Where should the access token from the identity provider be kept in a BFF design?

  • Prefer SSO via OIDC with PKCE. Keep tokens on the server; give the browser an HttpOnly cookie.
  • Permissions = action × entity group. Add attributes (time, booking, limits) when roles are too coarse.
  • Hide in the UI for comfort; enforce on the server for security.

20.4 Audit logging

An audit log answers "who changed what, when, from where, and why?". It is different from a debug log. A debug log helps developers and may be rotated after a week. An audit log is a record of human and system actions and may need to be kept for a year or more. It answers questions like "why was the server room at 29 °C on Sunday?" or "who disabled that alarm?".

FieldExampleWhy
Timestamp (UTC)2026-03-02T09:14:07.312ZOrder events across systems. Show local time in the UI only.
Actoruser:j.nowak, panel:lobby-1, schedule:weekdayHumans, devices and automation all act.
Action + targetsetpoint.write ahu1.sat_spWhat was done to what.
Old → new value18.0 → 16.0Lets you reverse a change.
Outcomeok, denied, failed: timeoutDenied attempts are security signals.
SourceIP, session ID, client typeTells a phone from a wall panel.
Reason (optional)"Contractor request, ticket 4411"Required for overrides in some sites.

Rules that make the log trustworthy:

  • Append-only. The application account may insert, never update or delete. Retention jobs run under a different account.
  • Written before the effect is confirmed. Record the intent, then the outcome. A crash in between still leaves a trace.
  • Tamper evidence. Each record can include a hash of the previous one. Editing a row breaks the chain. Shipping copies to a separate log server (syslog, a SIEM) is even stronger.
  • No secrets, minimal personal data. Never log passwords or tokens. Under GDPR, user IDs in an audit log are personal data. Define the purpose and retention period.
  • Searchable. Index by time, actor and target. Nobody reads a million lines by eye.

Try it: act and watch the log

A hospital wing reported a ward too cold overnight. The audit log showed a setpoint change from 22 °C to 18 °C at 02:10 by a wall panel in the ward corridor, during a night-shift session that had never timed out. The fix was twofold: a shorter idle timeout on corridor panels, and a "reason required" prompt for setpoint changes larger than 2 K.
Log the resolved target, not just what the browser sent. If the request said "room 2.14" but the backend mapped it to vav_2_14b, record both. Otherwise mapping bugs become invisible.

Why should denied attempts be logged too?

  • Record actor, action, target, old/new value, outcome, source and time in UTC.
  • Append-only, tamper-evident, separate from debug logs.
  • Automation and devices are actors too. Log them.

20.5 Kiosk and wall panel deployments

Many front ends end up on a wall: a 10-inch tablet beside a meeting room door, a 24-inch touch screen in a control room, a TV in a plant room. These run 24/7 for years with nobody watching them. That changes the engineering.

ConcernTypical answer
Locked-down browserChromium in kiosk mode (--kiosk) on a small Linux box; Android with a kiosk browser app or a device-owner lock task mode; iPadOS Guided Access or managed Single App Mode.
IdentityOne device account per panel, bound to a narrow role. Revocable without touching other panels.
PowerPoE (802.3at gives up to about 25 W at the device) or a fixed supply. Avoid tablets sitting on a charger at 100 % for years: battery swelling is a known failure. Some devices offer a charge limit.
Burn-in and brightnessDim at night, blank after inactivity, wake on touch or presence. OLED screens burn in static layouts.
UpdatesManaged via MDM or configuration management. Test on one panel first.
RecoveryWatchdog reloads the page if the app stops responding; nightly reload clears memory leaks.
PhysicalRecessed mounts, no exposed USB, wired network where possible.

The hardest problem is honesty about state. A panel that lost its connection still shows the last values. To a passer-by they look live. The UI MUST show connection status and age of data. A common pattern: after 2 × the heartbeat interval with no message, grey all values and show "Connection lost, retrying". Disable controls until the snapshot is back, so nobody presses a button that goes nowhere.

Try it: what does the panel show?

A conference centre mounts 42 PoE tablets beside room doors. Each runs a kiosk browser pointed at /panel/<room-id> with a device token. The panel shows the booking, room temperature and three buttons: Lights, Blinds, Presentation. The screen dims to 10 % after 2 min without presence and blanks between 23:00 and 06:00. A central page lists every panel with its last heartbeat, so a dead one is found before a guest complains.
Never put an admin session on a public panel "just for setup" and forget it. A wall panel is physically accessible to anyone in the building. Treat its role as public.

A panel lost its connection a minute ago. What is the right behaviour?

  • Kiosks need a locked browser, a device account with a narrow role, and remote management.
  • Show connection state and data age. Stale data MUST look stale.
  • Plan for power, burn-in, watchdog reloads and physical access.

20.6 HMI design principles (ISA-101)

ANSI/ISA-101.01-2015, "Human Machine Interfaces for Process Automation Systems", describes how to design, build and maintain operator screens. It came from process industries, after incident reviews found that cluttered, colourful screens hid the one value that mattered. The ideas, often called high-performance HMI, transfer well to buildings.

Core principles

PrincipleIn practice
Grey normal, colour abnormalBackgrounds and normal equipment are neutral grey. Saturated colour is reserved for alarms and abnormal states, so it pops out.
Consistent colour meaningRed means one thing everywhere (e.g. high-priority alarm). Do not use red for "pump running" on one screen and "fault" on another.
Never colour aloneAdd shape, text or an icon. About 1 in 12 men has some colour vision deficiency, mostly red-green.
Information, not dataShow 18.4 °C against its normal band, or a trend, not just a number.
Display hierarchyLevel 1 overview, level 2 unit (e.g. one AHU), level 3 detail, level 4 diagnostics.
Minimal decorationNo 3D pipes, gradients or spinning fans. Animation draws the eye, so save it for alarms.

The colour-for-abnormal rule is not taste. It follows from how attention works: a single saturated element in a grey field is found almost instantly, regardless of how many other items are on screen. In a screen where everything is colourful, finding the odd one out takes a serial search that grows with the item count.

Compare: find the problem

Display hierarchy

A plant room overview is redrawn from a vendor page with animated green fans and blue water to a grey line drawing. Each temperature gets a small bar with its normal band. After the change, a supply temperature drifting 3 K above band is visible from across the room, because it is the only orange item on the screen.
Do not copy ISA-101 slavishly into a lobby panel for guests. The standard targets trained operators. Public panels still benefit from calm, neutral design, but a guest needs plain words and big buttons, not a P&ID.

Why is "pump running = green" discouraged in high-performance HMI?

  • Grey for normal, saturated colour only for abnormal. One meaning per colour.
  • Never rely on colour alone. Add shape and text.
  • Structure screens in levels from overview to diagnostics.
