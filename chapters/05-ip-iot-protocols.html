Chapter 05

IP and IoT protocols

The protocols that carry building data over Ethernet, Wi-Fi and low-power radio: the industrial classics (Modbus TCP, BACnet/IP, OPC UA), the web family (REST, WebSocket, webhooks), network management (SNMP), smart-home meshes and cloud APIs, and finally the data models that give all these numbers meaning.

5.1 Modbus TCP

Modbus was created by Modicon in 1979 for its PLCs. It survived because it is tiny: a client asks, a server answers, and the whole application layer fits on a few pages. Modbus TCP (published in 1999) takes the exact same request and response, called the PDU (protocol data unit), and carries it in a TCP connection on port 502 instead of an RS-485 line.

The terms changed in 2020: the specification now says client/server instead of master/slave. The client (a BMS, SCADA or gateway) always starts. The server (a chiller, energy meter or VFD) never speaks unless asked. There is no discovery, no events and no data types beyond bits and 16-bit words.

The data model: four tables

Discrete inputs1 bitread only02—1xxxx

On the wire, every address is 0-based. Many manuals use the legacy 1-based notation, so "register 40001" is sent as address 0 with function code 03. This off-by-one is the single most common Modbus integration bug. If the values you read look like the neighbour of the right value, shift the address by one.

RTU frame vs TCP frame

Both frames carry the same PDU: a function code plus data. What wraps it differs:

  • RTU (serial): 1 byte slave address, the PDU, then a 2-byte CRC-16 (low byte first). Frames are separated by 3.5 character times of silence.
  • TCP: a 7-byte MBAP header in front of the PDU, and no CRC because TCP and Ethernet already check integrity. The MBAP header holds: transaction ID (2 bytes, chosen by the client, echoed by the server), protocol ID (2 bytes, always 0), length (2 bytes, number of bytes that follow: unit ID + PDU) and unit ID (1 byte).

The PDU is at most 253 bytes. That is why one read is capped at 125 registers (FC03/04) or 2000 coils, and one multi-register write at 123 registers.

Try it: build a request

Data types and byte order

Modbus knows only 16-bit registers. Everything else is a convention the device manual must state:

  • Scaled integers. 215 in a register with scale 0.1 means 21.5 °C. Signed values use two's complement: 0xFFF6 is −10, i.e. −1.0 °C.
  • 32-bit values (float32, uint32 energy counters) use two registers. Bytes inside a register are big-endian, but word order varies by vendor: ABCD, CDAB, BADC, DCBA. A temperature that reads as 1.4e−38 or 2.3e+12 is almost always swapped words.
  • Bit fields. One status register often packs 16 alarms.

Gateways and the unit ID

On a native Modbus TCP device the unit ID is usually ignored (often 1 or 255). On a TCP-to-RTU gateway it is the address of the serial device behind it. One gateway can expose 30 meters on one IP address, each a different unit ID. The gateway then serialises all requests onto one slow RS-485 line, so poll budgets from Chapter 04 still apply.

Many small devices accept only a few simultaneous TCP connections (often 1 to 8). If a BMS, a commissioning laptop and a cloud logger all connect, the last one may be refused or may knock out another. Plan one owner per device, and let others read through it.

Exceptions

When a request is invalid the server answers with the function code plus 0x80 and an exception code: 01 illegal function, 02 illegal data address, 03 illegal data value, 04 server device failure, 0B gateway target device failed to respond. No answer at all means a timeout, which is a different problem (wrong IP, wrong unit ID behind a gateway, or a dead line).

A typical office AHU controller publishes a register map: holding register 0 is the supply air setpoint ×10, input register 10 is supply air temperature ×10 (signed), input registers 20–21 are a float32 fan power in CDAB order, coil 0 is the run command. A BMS reads input registers 10–21 in one FC04 request every 10 s and writes register 0 only when an operator changes the setpoint.
Modbus has no authentication and no encryption. Anyone who reaches port 502 can write a setpoint or stop a fan. Keep Modbus on an isolated OT VLAN and never forward port 502 to the internet. The newer "Modbus/TCP Security" profile wraps Modbus in TLS on port 802, but few building devices support it.

A manual lists "Supply temperature: 30011". Which request reads it?

  • Modbus TCP = the serial PDU + a 7-byte MBAP header, no CRC, port 502.
  • Four tables, 0-based addresses on the wire, 125 registers per read at most.
  • Scaling, signedness and word order are vendor conventions. Read the manual.
  • No security, no discovery, no events. Isolate it.

5.2 BACnet/IP: objects, services, BBMD

BACnet (ASHRAE 135, also ISO 16484-5) was designed for buildings from the start. Where Modbus gives you a numbered register and a manual, BACnet gives you a self-describing object with a name, units, status and alarm limits that any client can read. It runs over several data links: MS/TP on RS-485 (Chapter 04), Ethernet, and most commonly today BACnet/IP, which uses UDP port 47808 (0xBAC0).

Devices and objects

Every BACnet device has exactly one Device object whose instance number (0 to 4 194 302) must be unique on the whole BACnet internetwork, not just the subnet. All other data lives in objects identified by type + instance, e.g. analog-input,3. Each object has properties; the most important is present-value. Click an object to see its properties.

The priority array

Commandable objects (outputs, and some values) do not have one present-value that the last writer wins. They have a 16-slot priority array. Each writer writes at its own priority. The present value is the value of the lowest-numbered (highest priority) slot that is not NULL. Writing NULL is called relinquishing. When every slot is NULL, the object falls back to relinquish-default.

Standard meanings: 1 manual life safety, 2 automatic life safety, 5 critical equipment control, 6 minimum on/off, 8 manual operator, 16 the lowest (schedules typically). Slots 3, 4, 7 and 9–15 are site-defined.

The classic BACnet mistake: a front end writes at priority 8 and never relinquishes. The schedule at 16 keeps running but has no effect, forever. Writing 0 or "off" does not release a slot; only writing NULL does. Good front ends show the active priority and offer a "release" button.

Discovery and broadcasts: why BBMDs exist

Who-Is is a broadcast. IP routers do not forward broadcasts, so a Who-Is sent on 10.1.10.0/24 never reaches a controller on 10.1.20.0/24. BACnet solves this with a BBMD (BACnet Broadcast Management Device) on each subnet. BBMDs hold a Broadcast Distribution Table (BDT) listing their peers. A BBMD that hears a local broadcast wraps it in a Forwarded-NPDU and unicasts it to each peer, which re-broadcasts it on its own subnet.

A single PC that sits elsewhere (a VPN laptop) can join as a foreign device: it sends Register-Foreign-Device to one BBMD with a time-to-live and then receives broadcasts by unicast.

Inside a BACnet/IP packet

A BACnet/IP datagram stacks three headers: BVLC (4 bytes: type 0x81, function, length; it says whether this is an original unicast 0x0A, original broadcast 0x0B or forwarded 0x04 message), NPDU (network layer: routing to other BACnet networks such as an MS/TP trunk behind a router) and APDU (the service request). A BACnet router between IP and MS/TP rewrites the NPDU so the workstation can address network 5, MAC 12 on the serial trunk.

Two common faults: duplicate device instances (two controllers shipped with the default instance, one of them "disappears" at random), and two BBMDs on the same subnet, which makes every broadcast arrive twice and can create broadcast storms. One BBMD per subnet, unique instances site-wide.

BACnet/SC (Secure Connect, added in 2019) replaces UDP broadcasts with TLS-encrypted WebSocket connections to a hub, using certificates. It removes BBMDs and adds real security, but needs newer devices.

A 40-room hotel has room controllers on four MS/TP trunks behind two BACnet/IP routers, plus a chiller and two AHUs on the plant VLAN. The integrator assigns device instances by building, floor and trunk (e.g. 1 03 05 → 10305), enables BBMD on one router per VLAN, and has the front end subscribe COV to room temperatures while writing setpoints at priority 8 and occupancy at 16.

Slots 8 = 22.0 and 16 = 19.0, all others NULL, relinquish-default 21.0. The operator writes NULL at 8. What is present-value?

  • BACnet data = objects with properties. Device instance numbers must be unique site-wide.
  • Commandable objects use a 16-level priority array. Release with NULL, not with 0.
  • Prefer COV and ReadPropertyMultiple over polling single properties.
  • Broadcasts stop at routers. One BBMD per subnet, or a foreign device registration.

5.3 OPC UA

OPC UA (Unified Architecture, IEC 62541) came from industrial automation. Its ancestor "OPC Classic" was tied to Windows DCOM. OPC UA is platform-independent, runs from small embedded servers to cloud services, and in buildings appears in PLC-based plant (Siemens S7-1500, Beckhoff, B&R), in large energy centres and in SCADA-to-IT integration.

Where BACnet fixes a set of object types, OPC UA gives you a meta-model: a graph of nodes joined by typed references. Vendors and industry groups define their own types on top. The graph is called the address space.

The address space

Every node has a NodeId (a namespace index plus an identifier: number, string, GUID or bytes, e.g. ns=2;s=AHU1.SupplyAirTemp), a NodeClass and attributes. There are eight node classes: Object, Variable, Method, ObjectType, VariableType, ReferenceType, DataType and View. Click a node.

Services and subscriptions

A client opens a secure channel and a session, then uses services: Browse (walk references), Read, Write, Call (invoke a method) and HistoryRead. For live data it creates a subscription containing monitored items. Each item has a sampling interval (how often the server checks the value), a queue size and optionally a deadband filter. The subscription has a publishing interval: the server sends one notification message per interval with all changes since the last. If nothing changed, it sends keep-alives.

Security

Each endpoint advertises a security mode (None, Sign, SignAndEncrypt) and a security policy (the algorithm suite, e.g. Basic256Sha256 or Aes256_Sha256_RsaPss). Client and server authenticate each other with application instance certificates, then the user logs in with anonymous, username/password or certificate tokens. The first connection usually fails until an administrator moves the client certificate from the server's "rejected" folder to "trusted". This is by design, not a bug.

Information models and PubSub

Companion specifications define standard types for a domain, so every vendor's pump looks the same (e.g. the Pumps and Vacuum Pumps spec, or machinery and energy models). PubSub (Part 14) lets servers publish to MQTT brokers or UDP multicast without client sessions, which suits fleet and cloud use.

A district heating substation runs on a PLC with a built-in OPC UA server. The BMS gateway connects with SignAndEncrypt, browses Objects/Substation/HeatExchanger1, and subscribes to 12 variables with a 1 s sampling interval, a 5 s publishing interval and a 0.1 K deadband on temperatures. Only changes travel, each with a source timestamp and a status code such as Good or Bad_CommunicationError.

An OPC UA client connects for the first time with SignAndEncrypt and is refused. The likely cause is…

  • OPC UA = a typed graph of nodes and references, browsed at runtime.
  • Subscriptions with monitored items push changes with timestamps and status codes.
  • Security is built in: certificates both ways, plus user authentication.

5.4 REST, WebSocket and webhooks

Newer devices, gateways and BMS platforms expose web APIs. Three patterns cover almost everything. They differ in one question: who starts the conversation, and when?

REST over HTTP

Resources have URLs; you act on them with HTTP methods. GET reads, PUT replaces, PATCH changes part, POST creates or triggers. Status codes tell you what happened: 200 OK, 201 Created, 204 No Content, 400 bad request, 401 not authenticated, 403 not allowed, 404 not found, 409 conflict, 429 too many requests, 5xx server error. REST is stateless: every request carries its own authentication, usually a bearer token.

GET /api/v1/points/ahu1.supply_air_temp HTTP/1.1
Host: gateway.plant.local
Authorization: Bearer eyJhbGciOi...

HTTP/1.1 200 OK
Content-Type: application/json
ETag: "a91f"

{"id":"ahu1.supply_air_temp","value":17.8,"unit":"°C",
 "quality":"good","ts":"2026-03-04T08:15:02Z"}

REST is perfect for configuration and commands. For live values it forces polling: the client asks again and again, most answers say "nothing changed", and a change is seen only at the next poll.

WebSocket

A WebSocket starts as an HTTP request with Upgrade: websocket (RFC 6455). The server answers 101 Switching Protocols and the TCP connection stays open as a two-way message channel. The server can now push a change the moment it happens. The cost: the server must keep state per client, and the client must handle reconnects, resubscribe and fetch a fresh snapshot after a gap, because messages sent while it was disconnected are lost. Ping/pong frames detect dead connections through NAT and proxies.

→ {"id":7,"type":"subscribe","points":["ahu1.*"]}
← {"id":7,"type":"result","success":true}
← {"type":"event","point":"ahu1.supply_air_temp","value":18.1,"ts":"…08:15:09Z"}

Webhooks

A webhook reverses the direction. You register a URL with a service; when something happens, the service sends an HTTP POST to you. No open connection, no polling. But your endpoint must be reachable from the sender (often from the internet), must verify the request is genuine (usually an HMAC signature header computed with a shared secret), must answer quickly with 2xx, and must tolerate retries and duplicates, because senders retry on timeouts. Use the event ID to make handling idempotent.

A typical gateway pattern: on start-up the client calls GET /points to load a full snapshot, then opens a WebSocket and subscribes to changes. Commands go as POST /points/{id}/command so they get a clear status code. After any reconnect it repeats the snapshot. The same pattern appears in Home Assistant's WebSocket API, in many PV inverter gateways and in most modern BMS front ends.
Do not poll a cloud API every second "to be safe". You will hit 429 rate limits, and a locked-out API key stops all control. Use push when it exists, back off on 429 using the Retry-After header, and cache.

A dashboard on a laptop must show a room temperature within one second of a change. The device API offers REST and WebSocket. Best choice?

  • REST for snapshots, configuration and commands. Polling trades load for latency.
  • WebSocket for live push over an outbound connection. Always resync after reconnect.
  • Webhooks need an inbound endpoint, signature checks and idempotent handling.

5.5 SNMP

The Simple Network Management Protocol is how IT monitors network gear, and buildings are full of network gear: switches, UPSs, PDUs, firewalls, NAS units, access points, even some generators and precision air conditioners. A BMS that watches the UPS over SNMP knows about a mains failure before the server shuts down.

Managers, agents, MIBs and OIDs

A manager (the monitoring system) talks to an agent on the device. The agent exposes values identified by an OID (object identifier), a path in a global tree such as 1.3.6.1.2.1.1.3.0. A MIB file is the dictionary that gives these numbers names, types and meaning. Standard MIBs (RFC-defined) live under 1.3.6.1.2.1 (mib-2). Vendor MIBs live under 1.3.6.1.4.1.<enterprise number>. Click through the tree.

Operations

Requests go to UDP 161 on the agent. Traps and informs go to UDP 162 on the manager. A trap is fire-and-forget over UDP, so it can be lost; an inform (v2c and v3) is acknowledged and retried. Good practice: use traps for speed, but also poll the key values every 30–60 s so a lost trap is caught.

Versions and security

VersionAuthenticationEncryptionNotes
v1Community string in clear textNone32-bit counters only. Legacy.
v2cCommunity string in clear textNoneAdds GetBulk, 64-bit counters, informs. Still the most common.
v3User-based (USM), HMAC-SHAAES (privacy)Levels noAuthNoPriv, authNoPriv, authPriv. Use authPriv.
The defaults "public" (read) and "private" (write) are still shipped on many UPS and PDU cards. A write community lets anyone on the network switch off outlets on a PDU. Change them, disable write access if you do not need it, prefer v3 authPriv, and limit which manager IPs the agent answers.

Counters and rates

Traffic counters such as ifInOctets only ever increase and wrap at 2³² (about 4.3 GB). On a 1 Gbit/s link that is about 34 seconds at full load, so use the 64-bit ifHCInOctets. A rate is (value₂ − value₁) ÷ time, with care at a wrap or an agent reboot (sysUpTime goes backwards).

A server room UPS with an SNMP card uses the standard UPS-MIB (RFC 1628). The BMS polls upsEstimatedChargeRemaining and upsEstimatedMinutesRemaining every 30 s, and receives a trap on upsTrapOnBattery. Its rule: on battery for 2 min → alert; minutes remaining below 10 → start the graceful shutdown of virtual machines.

Which statement about SNMP traps is true?

  • Manager polls agent on UDP 161; agent sends traps to UDP 162.
  • OIDs are paths in a global tree; MIBs give them names. mib-2 is standard, enterprises is vendor.
  • v2c is clear text. Use v3 authPriv and change default communities.

5.6 Zigbee, Z-Wave, Thread, Matter

Battery sensors and retrofit actuators rarely use Wi-Fi: it drains batteries in weeks. They use low-power radios that form a mesh, where mains-powered devices relay messages for others. Three radio networks dominate, and Matter sits on top as a shared application language.

Roles in a mesh

  • Coordinator (Zigbee) / controller (Z-Wave) / border router (Thread): forms the network and connects it to the rest of the world.
  • Router: mains powered, always listening, forwards traffic. Smart plugs, wired switches, many bulbs.
  • End device (sleepy): battery powered, sleeps most of the time, talks only to its parent router, which stores messages for it until it wakes and polls.

Matter (CSA, first release 2022) is not a radio. It defines device types, clusters and secure commissioning (often over Bluetooth LE, with a QR code), and runs on IP. Its key promises for buildings are local control without a cloud and multi-admin: the same device can belong to several controllers at once. Thread is the low-power transport it is usually paired with.

Practical rules

  • Build the router backbone first (plugs, wired switches), then add battery devices.
  • Keep Zigbee on channels that avoid your Wi-Fi: Zigbee 15, 20 and 25 sit between Wi-Fi channels 1, 6 and 11.
  • Do not cut power to routing bulbs with a wall switch; the mesh loses a relay each time.
  • Put the coordinator USB stick on an extension cable, away from USB 3 ports, which emit 2.4 GHz noise.
  • Treat "no reading for 2 h" from a battery sensor as a fault, not as "nothing happened".
A 40-room hotel retrofit uses Zigbee radiator thermostats and window contacts. Each corridor has two mains-powered smart plugs acting as routers, so every room has at least two parents within range. The gateway watches each device's "last seen" time and link quality, and raises a maintenance ticket when a battery falls below 20 %.

In a Thread network, the only border router fails. What happens?

  • Routers are mains powered and relay; end devices sleep and need a parent.
  • Zigbee and Thread share 2.4 GHz with Wi-Fi; Z-Wave uses sub-GHz.
  • Matter is an application layer over IP: local, multi-admin, usually on Thread or Wi-Fi.

5.7 Cloud APIs (Tuya) and their risks

Many cheap devices (plugs, thermostats, curtain motors, heat pump Wi-Fi modules) are controlled through the manufacturer's or platform's cloud. Tuya is the best-known example: thousands of brands ship Tuya modules under their own name. Integration is done by creating a developer project on the cloud platform, linking the user account, and calling a REST API (plus, on some platforms, a push message channel) with signed requests and a short-lived access token.

The dependency chain

When the BMS sends "set 21 °C" through a cloud, the command travels a long way to reach a device that may be three metres from the BMS server. Every link can break. Click a link to break or restore it.

Some cloud devices also accept local commands when you know their device key, and community projects such as local Tuya integrations use this. It removes the cloud from the control path, but the key is obtained from the cloud once and may change if the device is re-paired. Treat it as a useful workaround, not a supported interface.

A small office uses Wi-Fi heat pump controllers that only offer a cloud API. During an ISP outage on a cold Monday morning, the BMS cannot raise the setpoints after the weekend setback; the units stay at 16 °C until someone uses the wall controller. The fix: a Modbus adapter for the heat pumps, with the cloud kept only for the installer's remote diagnostics.

Which cloud-only device is the most acceptable in a building?

  • A cloud command depends on Wi-Fi, ISP, DNS, the vendor, your account and the API all working.
  • Rate limits, token expiry and API changes are failures too.
  • Use cloud-only devices only where losing them is acceptable. Prefer local APIs.

5.8 Data modelling: Haystack, Brick

Every protocol above delivers numbers with names chosen by whoever programmed the controller: AHU1_SAT, L03.ZN12.RmTmp, analog-input,3. A human can guess; software cannot. A semantic model describes what each point is, what equipment it belongs to and how equipment relates, in a machine-readable way. Then an analytics rule written once ("alarm if supply air temperature deviates from setpoint for 30 min") runs on any building.

Project Haystack: tags

Haystack (project-haystack.org) describes entities with tags. Marker tags carry meaning by presence (ahu, point, sensor, temp, air, discharge). Value tags hold data (dis:"AHU-1 Discharge Temp", unit:"°C"). Ref tags link entities (equipRef, siteRef, spaceRef). Queries use filters such as point and temp and air and discharge and equipRef->ahu. Haystack 4 added formal definitions (defs) and standard prototypes so tag sets are consistent.

Brick Schema: classes and relationships

Brick (brickschema.org) uses RDF and an ontology. Each entity is an instance of a class from a hierarchy (brick:Supply_Air_Temperature_Sensor is a brick:Temperature_Sensor is a brick:Sensor is a brick:Point). Entities are linked by relationships: hasPoint, feeds, hasPart/isPartOf, hasLocation. Queries use SPARQL, and reasoning follows the class hierarchy, so a search for Temperature_Sensor finds every subtype. ASHRAE 223P builds on similar ideas as a formal standard.

An analytics vendor connects to a portfolio of 12 office buildings with different BMS brands. Instead of writing rules per building, each site's points are tagged once. The rule "simultaneous heating and cooling" becomes: for every ahu, find a cmd and valve and hot point and a cmd and valve and chilled point, and flag hours where both are above 10 %. What does Brick's class hierarchy give you that a flat point name does not?

  • Protocols move values; semantic models say what the values mean.
  • Haystack: tags and refs, filter queries. Brick: RDF classes and relationships, SPARQL.
  • Model equipment and relationships at commissioning time.
