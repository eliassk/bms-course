Chapter 06

MQTT in depth

MQTT has become the lingua franca between gateways, controllers and supervisory software. It looks trivially simple, and that is the trap: topic design, QoS, retained messages and session handling decide whether a system is robust or quietly wrong. This chapter takes the protocol apart piece by piece.

6.1 Publish/subscribe model and why it fits buildings

Most building protocols you met in Chapters 04 and 05 are request/response: a client asks "what is holding register 40001?" and a server answers. The client must know every server, must poll on a timer and must repeat the question even when nothing has changed.

MQTT (originally "MQ Telemetry Transport", now just MQTT) inverts this. Clients never talk to each other. Every client opens one TCP connection to a central broker. A client publishes a message to a topic, a UTF-8 string such as site/ahu1/supply_temp. Other clients subscribe to topic filters. The broker routes each message to every matching subscriber. Publishers do not know who listens; subscribers do not know who publishes.

DecouplingMeaningWhy it helps in a building
SpacePublisher and subscriber never know each other's address.Add a dashboard, a historian or an energy app without touching the gateway.
TimeWith retained messages and persistent sessions, they need not be online together.A front end that restarts gets the last known state at once.
SynchronisationPublishing does not block on consumers.A slow historian cannot stall the lighting gateway.

MQTT is standardised by OASIS. Version 3.1.1 (2014) is also ISO/IEC 20922:2016. Version 5.0 (2019) added reason codes, properties and more (see 6.13). The default ports are 1883 (plain TCP) and 8883 (TLS). WebSocket transport is common for browsers. The fixed header is just 2 bytes, so a small sensor value fits in a packet of a few dozen bytes.

Try it: polling mesh vs broker star

Event-driven, report by exception

A well-behaved MQTT device publishes on change (with a deadband, e.g. 0.1 K) plus an occasional heartbeat. A room sensor that is stable for an hour sends almost nothing. Compare a BMS polling 2000 Modbus points every 5 s: 400 requests per second, almost all returning the same value.

A 40-room hotel has a lighting gateway, a heating controller per floor and a meter gateway. Each publishes to one broker. The front desk tablet, a historian and an alerting service subscribe. When an energy consultant later wants the meter data, they add one subscriber with read-only rights. No gateway is reconfigured.
The broker is now a single point through which everything flows. It must be monitored, backed up and, for critical sites, made highly available (6.15). Control loops must still never depend on it.

8 gateways and 4 consumers. How many TCP connections does a broker architecture need?

  • Clients talk only to the broker. Topics, not addresses, connect producers and consumers.
  • Pub/sub decouples space, time and synchronisation.
  • Report by exception plus heartbeat beats blind polling.

6.2 Brokers: Mosquitto, EMQX, HiveMQ

The broker is the only server in MQTT. It accepts connections, authenticates clients, checks permissions, matches topics, stores retained messages and queues messages for offline persistent sessions. Brokers differ mostly in scale, clustering and management, not in protocol behaviour.

BrokerLanguage / licenceStrengthsTypical fit
Eclipse MosquittoC, EPL/EDL open sourceTiny (a few MB RAM), simple config file, plugin auth, bridge support. Single-threaded, no native clustering.One building, an edge box, a Raspberry Pi, a Home Assistant add-on.

Inside a broker

A minimal Mosquitto configuration

# /etc/mosquitto/mosquitto.conf  (Mosquitto 2.x)
per_listener_settings false
listener 1883 127.0.0.1        # local plain, for on-host services only
listener 8883                  # TLS for everyone else
certfile /etc/mosquitto/certs/server.crt
keyfile  /etc/mosquitto/certs/server.key
allow_anonymous false          # default since 2.0
password_file /etc/mosquitto/passwd
acl_file /etc/mosquitto/acl
persistence true               # keep retained + sessions across restarts
persistence_location /var/lib/mosquitto/

Since Mosquitto 2.0 a listener without explicit configuration only binds to localhost and anonymous access is off. Many "it worked on 1.6" problems come from that change.

A typical single-building edge server runs Mosquitto in a container next to the supervisory software. It holds 50–200 client connections and a few thousand retained topics, using under 20 MB of RAM. A property group with 60 sites instead runs a three-node EMQX cluster in a data centre, and each site's edge broker bridges selected topics up to it.

Which feature most clearly separates EMQX/HiveMQ from Mosquitto?

  • The broker authenticates, authorises, routes, retains and queues.
  • Mosquitto for one site; EMQX or HiveMQ when you need clustering and scale.
  • Mosquitto 2.x is secure by default: configure listeners and auth explicitly.

6.3 Topic design and naming conventions

A topic is a UTF-8 string of up to 65,535 bytes, split into levels by /. Topics are case-sensitive, need no prior declaration and cost nothing to create. That freedom is why topic design is the most important decision in an MQTT system: it is your data model and your permission model at once.

Wildcards (subscriptions only)

WildcardMatchesExample filterMatchesDoes not match
+exactly one levelsite/+/tempsite/r101/tempsite/f1/r101/temp
#zero or more levels; MUST be lastsite/f1/#site/f1, site/f1/r101/tempsite/f2/r201

Edge cases: # also matches the parent level itself. An empty level is valid (a//b has three levels). A leading slash creates an empty first level, so /site/x and site/x are different topics. Topics starting with $ (such as $SYS/…) are not matched by filters beginning with # or +.

Try it: wildcard matcher

A naming convention that scales

A good pattern goes from general to specific, then splits state from commands:

<site>/<area>/<device>/<point>[/set]

hotel/f2/room214/temp            21.4      state, retained
hotel/f2/room214/setpoint        21.0      state, retained
hotel/f2/room214/setpoint/set    22.0      command, not retained
hotel/f2/room214/availability    online    LWT (6.6)
  • Use lowercase, ASCII, no spaces. snake_case for multi-word levels.
  • Keep identifiers stable. Use an asset ID, not a display name that a client might rename.
  • Never put changing values in the topic (no …/temp/21.4), and avoid timestamps or random IDs in levels: every unique topic costs broker memory.
  • Separate state topics (what is) from command topics (what someone wants). The device publishes the state after acting on the command. This closes the loop and shows failures.
  • Design so that ACLs follow the tree: "the lighting gateway may write hotel/+/lighting/#".
Avoid a subscriber on # in production. On a busy broker it receives every message, including high-rate telemetry it does not need, and it bypasses any thinking about ACLs.

Which topic does the filter site/+/ahu/# match?

  • + is one level, # is the rest (including zero levels) and must be last.
  • General to specific; state and command topics separated.
  • The topic tree is also the permission tree. Design both together.

6.4 QoS levels 0, 1, 2

Quality of Service is agreed per hop: publisher → broker, and separately broker → subscriber. The broker delivers to each subscriber at the lower of the published QoS and the QoS the subscriber asked for. TCP already guarantees ordered delivery on a live connection; QoS is about what happens when the connection breaks mid-message.

QoSGuaranteePacketsUse for
0 at most onceFire and forget. Lost if the link drops.PUBLISHHigh-rate telemetry where the next value replaces the old one.
1 at least onceResent until acknowledged. May arrive twice.PUBLISH, PUBACKMost state and commands. Make handlers idempotent.
2 exactly onceFour-step handshake removes duplicates.PUBLISH, PUBREC, PUBREL, PUBCOMPCounters or events where a duplicate is harmful (e.g. "add 1 to the visitor count").

Each QoS 1/2 message carries a 16-bit packet identifier. On a resend after reconnect, the sender sets the DUP flag. The receiver of QoS 2 remembers the packet ID between PUBREC and PUBREL, so a resent PUBLISH is acknowledged but not delivered again.

Try it: handshakes with packet loss

An office AHU gateway publishes supply temperature every 10 s at QoS 0: a lost sample is replaced 10 s later. Its alarm topic uses QoS 1 with retain, so a "filter dirty" alarm survives a Wi-Fi hiccup. A people-counter that publishes "+1" events uses QoS 2, or better, publishes an absolute total at QoS 1 so duplicates cannot do harm.
QoS is not end-to-end. A QoS 2 publish to a broker that delivers to a QoS 0 subscriber gives that subscriber QoS 0. And "exactly once" only covers MQTT; if the subscriber crashes after receiving but before writing to its database, the message is gone.

A device publishes at QoS 2. A dashboard subscribed with QoS 1. What does the dashboard get?

  • QoS is per hop; delivered QoS = min(published, subscribed).
  • QoS 1 is the workhorse. Make consumers idempotent.
  • Prefer absolute values over increments; then duplicates are harmless.

6.5 Retained messages and their traps

A PUBLISH with the retain flag tells the broker: store this as the last known value of the topic. The broker keeps exactly one retained message per topic. When a client later subscribes to a matching filter, the broker sends the retained message immediately. This is what makes MQTT feel like a live state database: a dashboard that reconnects shows every value at once instead of waiting for the next change.

To delete a retained message, publish an empty payload (zero bytes) with retain set. The broker removes it and delivers nothing to new subscribers.

Try it: an in-browser broker

The traps

TrapWhat happensFix
Retained commands…/boiler/set ON is retained. Months later the boiler controller reboots, subscribes, and gets "ON" again, even though someone switched it off locally.Never retain commands. Retain state only.
Stale valuesA sensor dies. Its last retained "21.4" stays forever and looks healthy.Pair with availability/LWT (6.6), add timestamps, or use MQTT 5 message expiry.
Ghost topicsA renamed device leaves its old retained topics behind. Dashboards show phantom devices.Clear with empty retained publishes during decommissioning.
Events retainedA "doorbell pressed" event retained replays on every reconnect.Events are not state: do not retain.
Persistence offThe broker restarts and every retained value is lost until devices publish again.Enable broker persistence, or make devices republish on reconnect.

How do you remove a retained message from site/ahu1/mode?

  • Retain = last known value, one per topic, delivered on subscribe.
  • Retain state, never commands or events.
  • Empty payload + retain clears it. Pair retained state with availability.

6.6 Last Will, birth messages, availability

A retained value tells you what a device last said. It does not tell you whether the device is still alive. MQTT solves this with the Last Will and Testament (LWT). In its CONNECT packet a client gives the broker a will topic, payload, QoS and retain flag. If the connection ends ungracefully, the broker publishes the will on the client's behalf.

"Ungraceful" means: keepalive timeout (6.7), TCP reset, a protocol error, or the network vanishing. A clean DISCONNECT packet discards the will (in MQTT 5 a client may ask for it to be sent anyway with reason code 0x04).

The common pattern is a birth/will pair on one retained availability topic:

  1. CONNECT with will …/availability = offline, retain, QoS 1.
  2. Immediately after CONNACK, publish …/availability = online, retain (the birth message).
  3. Before a planned shutdown, publish offline yourself, then DISCONNECT.

Try it: kill the gateway

A lighting gateway bridging a Helvar or DALI bus to MQTT publishes lighting/gw1/availability. A supervisory UI greys out every light of that gateway when it reads offline, instead of showing stale "on" states that nobody can change. An alerting rule fires if it stays offline for 2 minutes, and sends a "cleared" message when it is back.
The will is published only after the broker detects the loss. With a 60 s keepalive, that can take up to 90 s. Do not expect instant offline detection.

A gateway sends a clean DISCONNECT before rebooting for an update. What happens to its will?

  • LWT = message the broker sends for you if you vanish.
  • Birth "online" + will "offline", both retained, on one availability topic.
  • Detection time depends on keepalive: up to 1.5 × keepalive.

6.7 Sessions, keepalive, reconnect behaviour

Keepalive

In CONNECT the client declares a keepalive in seconds (0–65,535; 0 disables it). If the client has nothing else to send, it sends PINGREQ and the broker answers PINGRESP. If the broker hears nothing from the client for 1.5 × keepalive, it closes the connection and publishes the will. The client, in turn, treats a missing PINGRESP as a dead link and reconnects.

Why bother when TCP exists? A cable pulled on a switch two hops away does not reset the TCP connection. Without application keepalive, both sides can believe a dead connection is alive for many minutes, until TCP retransmission timeouts expire.

Sessions

A session is the state the broker keeps for a client ID: its subscriptions, QoS 1/2 messages in flight, and messages queued while offline. Whether it survives a disconnect depends on the CONNECT flags:

VersionSettingEffect
3.1.1cleanSession = 1New session each time; discarded on disconnect.
3.1.1cleanSession = 0Persistent session. Subscriptions remain; QoS 1/2 messages queue while offline. Kept until the broker's own expiry, if any.
5.0Clean Start + Session Expiry IntervalSeparated: Clean Start decides whether to resume, Session Expiry (seconds) decides how long the broker keeps it after disconnect.

The broker replies in CONNACK with Session Present. A client that sees 0 MUST re-subscribe. A robust client simply re-subscribes after every connect.

Reconnect behaviour

  • Back off. Retry 1 s, 2 s, 4 s … up to 30–60 s, plus random jitter. After a broker restart, 300 gateways reconnecting in the same second can overload it.
  • Unique client IDs. Two clients with the same ID kick each other off in a loop (the broker MUST disconnect the existing one). A classic symptom is a device that connects and disconnects every few seconds.
  • Republish state after reconnect, especially the birth message.
  • Bounded queues. A persistent session for a client that never returns will grow. Set broker limits (Mosquitto max_queued_messages) and session expiry.
A historian uses a persistent session at QoS 1 with client ID historian-01. During a 10-minute database maintenance it is offline; the broker queues around 6,000 messages and delivers them when it returns, so no samples are lost. The dashboards use clean sessions: they only care about the present, which retained messages provide.

Keepalive is 60 s. The client's network silently dies right after its last ping. When does the broker publish the will, at the latest?

  • Broker drops a silent client after 1.5 × keepalive.
  • Persistent sessions queue QoS 1/2 messages for offline clients; bound them.
  • Unique client IDs, exponential back-off with jitter, re-subscribe and republish on connect.

6.8 Payloads: plain values, JSON, schemas

MQTT does not care what the payload is. It is a byte array of up to 256 MB (268,435,455 bytes, limited by the remaining-length field). Brokers usually set a far lower limit. The format is a contract between publishers and subscribers that you must define yourself.

StyleExampleProsCons
Plain value, one topic per point…/temp → 21.4Trivial to consume, fine-grained retain and ACL, easy to read in tools.Unit, quality, timestamp must live elsewhere; many topics.
JSON object per device…/state → {"temp":21.4,"rh":45}Atomic snapshot, self-describing, carries metadata.Consumers must parse; one field change resends all.
Binary (Protobuf, CBOR)Sparkplug B (6.11)Compact, typed, schema-enforced.Not human-readable; needs tooling.

Try it: what does each format cost?

Rules that save you later

  • Use SI units and say which, in the payload, the topic or a documented schema. "21.4" in °F vs °C has broken real projects.
  • Use ISO 8601 UTC timestamps (2026-03-01T08:15:00Z) or epoch milliseconds. Never local time without an offset.
  • Send numbers as JSON numbers, booleans as true/false, not "ON" in one place and 1 in another.
  • Version the schema: {"v":2,…} or a topic level …/v2/….
  • Validate with JSON Schema at the consumer, and drop or flag invalid messages instead of crashing.
  • Add a quality flag when the source can be unreliable ("q":"good"|"stale"|"fault").
Zigbee2MQTT publishes one JSON object per device ({"temperature":21.4,"humidity":45,"battery":87,"linkquality":120}). Many Modbus gateways instead publish one plain value per register topic. Both work; mixing them without documentation is what hurts.

A JSON device payload changes one field out of 20 every second. What is the main cost?

  • The payload format is your contract; MQTT does not define it.
  • Plain values are simple; JSON adds atomic metadata; binary adds compactness and types.
  • Units, UTC timestamps, real types, versioning, validation.

6.9 Home Assistant MQTT discovery

MQTT gives you data but no metadata: a subscriber does not know that …/temp is a temperature in °C from a device called "Room 214 sensor". Discovery conventions fix that by publishing a description on a well-known topic. Home Assistant's discovery format is the most widely implemented (Tasmota, ESPHome, Zigbee2MQTT, many gateways).

The config topic is:

<discovery_prefix>/<component>/[<node_id>/]<object_id>/config
homeassistant/sensor/room214/temp/config

The payload is retained JSON. It names the state topic, device class, unit, a unique_id (needed for the entity to be editable in the UI) and a device block that groups entities. Abbreviations such as stat_t for state_topic are allowed to save bytes. An empty retained payload on the config topic removes the entity. Newer Home Assistant versions also support a single device-level discovery message (homeassistant/device/<id>/config) with a components map.

Home Assistant publishes its own birth message, online on homeassistant/status. Devices should resend their discovery configs when they see it, because a restarted Home Assistant may have lost non-retained ones.

Try it: from config to entity

Discovery configs are retained. If you change an object_id or unique_id without clearing the old config, you get duplicate entities. Clear old configs with an empty retained publish.

Why should a device listen to homeassistant/status?

  • Discovery = retained JSON on homeassistant/<component>/…/config.
  • unique_id and a device block make entities manageable.
  • Empty retained config deletes; resend configs on homeassistant/status = online.

6.10 Bridging fieldbus to MQTT (Modbus, DALI/Helvar)

Few field devices speak MQTT natively. A gateway sits between a fieldbus and the broker: it polls or listens on the bus, converts raw values to engineering units, publishes on change, and turns MQTT commands into bus writes. The gateway is where most integration bugs live, so it deserves care.

Try it: one Modbus register on its way to MQTT

The register address shown uses the common "3xxxx" notation for an input register; on the wire it is offset 0. Chapter 04 covers the off-by-one trap in detail.

Design checklist for a gateway

  • Scaling and type in a documented point map: register, data type (int16, uint32, float32), word order, scale, unit.
  • Deadband + heartbeat: publish when the value moves by more than the deadband, and at least every N minutes.
  • Per-point quality. After repeated bus timeouts, publish an unavailable state for that device instead of freezing the last value.
  • Command path: subscribe to …/set, validate range, write, read back, then publish the confirmed state.
  • Gateway availability via LWT, and separate per-device availability for bus devices.

DALI and Helvar style lighting

Lighting gateways map a different model. DALI addresses up to 64 control gear, 16 groups and 16 scenes per bus. A gateway typically exposes topics per group or per area such as lighting/f2/meeting1/level (0–100 %) and lighting/f2/meeting1/scene/set. Helvar routers organise lighting in groups and blocks with scenes; their gateways usually publish the active scene per group rather than every driver level. Publishing per-driver levels for hundreds of fittings floods the broker during a scene recall, when every fitting changes at once.

In a typical office, a Modbus TCP gateway polls 12 heat meters and 4 AHU controllers every 5 s (about 400 points). With a 0.2 K deadband and 10-minute heartbeat it publishes around 3 messages per second on average, instead of 80 if it published every poll.

A Modbus device stops answering. What should the gateway publish?

  • The gateway owns scaling, deadband, heartbeat and quality.
  • Commands: validate, write, read back, publish confirmed state.
  • Lighting: publish at group/scene level to avoid storms.

6.11 Sparkplug B for industrial MQTT

Plain MQTT leaves topic structure, payload format and state awareness to you. Sparkplug, an Eclipse Foundation specification (version 3.0, also ISO/IEC 20237:2023), defines all three for industrial use. It is popular in SCADA and manufacturing and appears in larger building and campus projects.

Topic namespace

spBv1.0/<group_id>/<message_type>/<edge_node_id>[/<device_id>]
spBv1.0/campus/DDATA/plantroom_gw/boiler2
TypeSent byMeaning
NBIRTH / DBIRTHEdge nodeNode / device is online. Lists every metric with name, alias, datatype and current value.
NDATA / DDATAEdge nodeChanged metrics only (report by exception), usually by alias.
NDEATH / DDEATHBroker (will) / edge nodeNode or device offline. NDEATH is registered as the MQTT will.
NCMD / DCMDHost applicationWrite a metric or ask for a rebirth.
STATEPrimary hostHost online/offline, on spBv1.0/STATE/<host_id> (retained JSON).

Payloads are Google Protocol Buffers with typed metrics, timestamps and a sequence number seq (0–255, wraps) on every message. A bdSeq number links each NBIRTH with the NDEATH registered in the same connection. Sparkplug messages are not retained (except STATE); state comes from births.

Try it: edge node state machine

A campus energy centre has an edge node per plant room. The SCADA host subscribes to spBv1.0/campus/#. On connect it reads all DBIRTH messages and instantly knows every boiler metric, its type and unit, without a hand-made point list. When a plant room loses its uplink the broker publishes NDEATH and the host marks all its metrics stale in one step.

A host application sees a DDATA with a seq gap (got 17 after 15). What should it do?

  • Sparkplug B fixes topic layout, Protobuf payloads and online/offline state.
  • BIRTH declares metrics; DATA sends changes; DEATH (as the will) marks offline.
  • seq and bdSeq detect gaps and stale deaths.

6.12 Security: users, ACLs, TLS

An open broker on a building network lets anyone read every value and, worse, write every command topic. Shodan regularly lists tens of thousands of anonymous MQTT brokers on the internet. Three layers close this:

  1. Authentication: who is this? Username/password (hashed on the broker, e.g. PBKDF2-SHA512 in Mosquitto's password file), client certificates (mutual TLS), or a plugin to LDAP, a database or JWT.
  2. Authorisation (ACL): what may this identity read and write? Per user, per topic pattern.
  3. Encryption: TLS on 8883 (or WSS) so passwords and values cannot be sniffed, and the client can verify the broker's certificate.

Mosquitto ACL syntax

# applies to all users
pattern read  site/+/+/availability
pattern readwrite clients/%c/#          # %c = client id, %u = username

user dali_gw
topic readwrite lighting/#

user dashboard
topic read  site/#
topic write site/+/+/setpoint/set

user historian
topic read  #

Access is denied unless a rule allows it. topic deny … explicitly blocks a subtree. Wildcard subscriptions are checked against the rules too: a read site/# rule covers a subscription to site/+/temp. Exact edge cases differ between brokers and versions, so test them.

Try it: ACL tester

Practical rules

  • One identity per device or service. Never share one "bms" account across all gateways.
  • Least privilege: gateways write their own subtree, UIs read state and write only …/set.
  • Keep plain 1883 bound to localhost, or remove it. Expose only 8883.
  • Put the broker on the OT network segment, never port-forward it to the internet. Use a VPN or a bridge with an outbound TLS connection for remote sites (6.15).
  • Rotate credentials when staff or contractors change; certificates make that easier at scale.

With the ACL above, may dashboard publish to site/f2/room214/temp?

  • Authenticate every client, authorise per topic, encrypt with TLS.
  • One identity per device; least privilege along the topic tree.
  • Never expose a broker directly to the internet.

6.13 MQTT 5 features

MQTT 5.0 kept the same packets and model but added properties (typed key-value fields in packet headers) and reason codes on every acknowledgement. Most modern brokers and client libraries support it; many embedded devices still use 3.1.1, and the two versions coexist on one broker.

Try it: message expiry on a retained value

Three historian instances should share the load of site/# without each storing every message. Which feature?

  • MQTT 5 = properties + reason codes, same model.
  • Expiry intervals fix stale retained data and immortal sessions.
  • Shared subscriptions scale consumers; request/response tidies commands.

6.15 Bridges, clustering, broker high availability

One broker is a single point of failure and a single location. Two different mechanisms address this, and they solve different problems.

BridgeCluster
WhatA broker acts as a client of another broker and forwards chosen topics.Several broker nodes behave as one logical broker with shared routing and sessions.
GoalConnect sites (edge ↔ cloud), filter and rename topics.Scale and survive the loss of a node.
StateEach broker has its own sessions and retained store.Sessions and subscriptions replicated across nodes.
ExamplesMosquitto connection blocks, EMQX/HiveMQ bridgesEMQX, HiveMQ, VerneMQ

Try it: edge bridge during an outage

High availability options

  • Single broker, fast restart. Container with restart policy, persistence on disk, monitoring. Often enough for one building: a 10-second outage is absorbed by client reconnect logic.
  • Active/standby pair. Two brokers behind a virtual IP (keepalived/VRRP). Retained state and sessions are not shared unless you add it, so clients must republish on reconnect.
  • Cluster of 3+ nodes behind a load balancer. Sessions survive a node loss. Odd node counts avoid split-brain.
  • Edge + central. Each site keeps a local broker so local control and UI keep working when the WAN fails; a bridge forwards to the centre and queues while offline.
Bridge loops: if two brokers both bridge # in both directions without prefixes, a message can bounce forever. Use distinct prefixes or MQTT 5 No Local, and forward only what is needed.
A retail chain with 120 stores runs Mosquitto on each store's edge server. Each bridges store/# out to a central EMQX cluster as chain/<store_id>/…, and receives only cmd/# back. When a store's internet is down for an hour, its HVAC and lighting UI work as normal and the central dashboard catches up when the bridge returns.

What keeps a building's local dashboard working when the WAN link to the central broker fails?

  • Bridges connect brokers; clusters make several nodes act as one.
  • Edge broker + bridge keeps a site autonomous during WAN loss.
  • Prefix bridged topics and forward only what is needed to avoid loops.
