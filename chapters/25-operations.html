Chapter 25

Commissioning, maintenance and troubleshooting

A BMS is only as good as the day it was proven to work, and every day after that. This chapter covers how systems are tested and accepted, which documents must exist, how drawings are used, how to keep a system healthy, how to find faults methodically, and how to work with the people who build it.

25.1 Commissioning and acceptance tests

Commissioning (Cx) is the documented process of proving that installed systems do what the design intent says they should. It is not "switching it on". A system can run, show green on every graphic and still be wrong: a valve wired in reverse, a sensor in the wrong duct, a sequence that never enters free cooling.

Commissioning starts long before installation. Good practice, described in guidance such as ASHRAE Guideline 0 and Standard 202, the CIBSE commissioning codes and BSRIA guides in the UK, and VDI 6039 in Germany, runs through the whole project. The names vary by country, but the stages look alike.

The phases

What a functional test looks like

A functional test is a script. It states the initial condition, the action, and the expected result with a tolerance and a time limit. "AHU works" is not a test. This is:

  1. Initial: AHU running, occupied mode, supply setpoint 19 °C, outdoor 8 °C.
  2. Action: override supply setpoint to 23 °C.
  3. Expected: heating valve opens, supply temperature reaches 23 ± 0.5 °C within 10 min, no overshoot above 24 °C, recovery wheel at 100 %.
  4. Record: trend export of setpoint, supply temp, valve position, wheel speed. Pass / fail. Initials of both witnesses.

Test the failure paths too. What happens when the frost thermostat trips, the supply sensor reads open circuit (for example below 3.6 mA), or the controller loses power and restarts? Many faults show up only in these paths, because normal operation is what everyone watches.

Interactive: a commissioning checklist

An office AHU passes its point-to-point test. In the functional test the engineer forces a high return CO₂ reading of 1,400 ppm. The outdoor damper should open to 100 %, but it stays at 30 %. The cause: the CO₂ sensor was configured as 0–10 V for 0–2,000 ppm in the controller, but the transmitter was set to 0–5,000 ppm. The BMS showed 560 ppm. Point-to-point had only checked that "a value arrives", not that it matched a reference meter.
Never accept "tested by the contractor" without evidence. A tick with no value, no trend and no date is a promise, not a test. Ask for a sample of tests to be repeated in front of you, around 10 % is a common choice.

Which test proves that a fire alarm signal actually shuts down the supply fans?

  • Commissioning proves design intent with evidence. Running is not the same as correct.
  • FAT → installation → point-to-point → functional → integrated → seasonal.
  • A test has an initial state, an action, an expected result with tolerance, and a record.
  • Test failure paths, not only normal operation.

25.2 Point lists and as-built documentation

The point list (also I/O list or points schedule) is the single most useful document in a BMS. It lists every physical and virtual point, where it lives and what it means. If the point list is right, almost every later task gets easier: tests, graphics, alarm setup, integration, troubleshooting.

The point-to-point test

Point-to-point (P2P) proves the chain from the field device to the supervisory screen, one point at a time. It usually needs two people: one in the field with a reference meter and radio or phone, one at the workstation. Step through the workflow below.

As-built documentation

The design drawings show what was planned. The as-built (or record) set shows what was actually installed, including every change made on site. Without it, the next engineer must reverse-engineer the building. Explore a typical structure:

A school renovation replaces a boiler and the hot water circuit pump. The contractor rewires the pump's run feedback to a spare input, DI7, because DI3 was damaged. Nobody updates the point list. Two years later the graphic shows the pump "stopped" while it runs, and a service engineer spends half a day tracing a fault that is just a documentation gap.
Software is part of the as-built. Controller programs, BMS database, graphics, and the exact tool and firmware versions MUST be handed over. A PDF of the wiring is useless if nobody can open the controller project.

During point-to-point, a room sensor shows 22.0 °C on the BMS. The reference meter reads 22.1 °C. What else must you check?

  • The point list is the backbone: tag, location, signal, address, alarm, trend, test status.
  • P2P proves identity (right point), value (against a reference) and direction (sign, polarity).
  • As-built includes software, versions and passwords transfer, not only drawings.

25.3 CAD/DWG drawings for BMS work

Most building drawings live in DWG, the native format of AutoCAD. Other tools such as BricsCAD, DraftSight and many others also read and write it. DXF is a documented exchange format, readable by more programs, including open-source ones. For viewing only, free viewers exist from Autodesk and others. Larger projects increasingly use BIM models, exchanged as IFC, but BMS engineers still spend most of their time with 2D plans and schematics.

Drawings a BMS engineer uses

Floor plansWhere sensors, controllers, panels and room devices sit.
SchematicsPlant diagrams: AHU, boiler, chiller with every sensor and actuator tagged.
Panel drawingsCabinet layout, terminal strips, power, fusing.
Wiring diagramsTerminal-to-terminal connections, cable numbers.
Network riserControllers, switches, bus segments per floor.
Cable routesTrays, risers, fire-stopping penetrations.

Layers and external references

A DWG is organised in layers: walls on one, ducts on another, BMS devices on a third. You can hide what you don't need. A disciplined project uses a layer naming standard (for example based on ISO 13567 or the US National CAD Standard) so that M-HVAC-DUCT or E-BMS-DEV mean the same thing everywhere.

External references (xrefs) let one drawing show another. The BMS plan references the architect's floor plan instead of copying it. When the architect moves a wall, the BMS plan updates. The catch: if you send the BMS drawing without its xrefs, the recipient sees devices floating in empty space. Use the CAD tool's "eTransmit" or "bind" function to package them.

Practical skills

  • Scale and units. Check whether the model is in millimetres or metres before measuring. A 6 m cable run measured as 6 mm is a classic error.
  • Blocks with attributes. A device symbol can carry tag, type and address as attributes. These can be extracted to a table and compared with the point list.
  • Redlines. On site, mark changes in red on a printed or PDF plan. These redlines become the input for the as-built.
  • Revision control. Every sheet has a revision letter or number and a revision table. Never work from an unrevisioned print.
An integrator extracts all BMS-DEVICE block attributes from 14 floor plans into a spreadsheet: 612 devices. The point list has 598 room-level points. A simple join finds 19 devices on drawings that are missing from the list and 5 in the list that are on no drawing. Fixing that before installation took one afternoon. After installation it would have meant 24 site investigations.
Do not treat a PDF export as the drawing. It loses layers, attributes and xrefs. Ask for the native DWG (or IFC) and keep PDFs only as a printable copy.

You open a BMS floor plan and see sensor symbols but no walls. The most likely reason is…

  • DWG is native, DXF is exchange, IFC is BIM. PDF is for printing.
  • Layers and xrefs organise drawings. Send xrefs with the drawing.
  • Device blocks with attributes can be checked against the point list automatically.

25.4 Preventive maintenance

Maintenance comes in three styles. Corrective maintenance fixes things after they break. Preventive maintenance does work on a schedule, whether or not anything looks wrong. Condition-based (or predictive) maintenance uses data to act when a measured value says it is needed. A BMS can drive the third style, because it already measures runtime, pressure drops and temperatures. European terminology for these is defined in EN 13306. In the UK, SFG20 is widely used as a library of maintenance tasks and intervals.

What to maintain on the BMS itself

Condition-based: let the BMS tell you

A filter is a good example. A fixed schedule might swap it every 6 months. A pressure sensor across the filter shows when it is actually loaded. Clean, a bag filter might show about 60–80 Pa. A typical change point is around 200–250 Pa, or whatever the filter maker specifies as final pressure drop. Try the estimator:

A building with 40 fan coil units and 4 AHUs logs runtime hours per fan. Instead of changing all filters twice a year, the work orders are triggered by runtime: every 2,500 h for fan coils, and by differential pressure for AHUs. Meeting rooms used twice a week now get filters every 18 months, the busy reception every 7 months.
The most common long-term BMS fault is a forgotten override. A valve left at 100 % "for testing" or a pump forced on in summer can run for years. An override report is the cheapest maintenance task there is.

You have a nightly backup of the BMS server. What is still missing for a reliable recovery?

  • Corrective, preventive, condition-based. A BMS enables the third.
  • Maintain the BMS itself: sensors, actuators, backups, firmware, batteries, alarms, clocks.
  • Schedule seasonal checks before the season, not when the first complaint arrives.
  • Review overrides regularly.

25.5 Troubleshooting method: layer by layer

Most failed troubleshooting is unstructured: change something, see if it helps, change something else. A faster method is to walk the layers, bottom up, and prove each one before moving on. It mirrors the network model you know from software: there is no point debugging the application if the cable is unplugged.

LayerQuestionTools
PhysicalIs there power? Is the signal on the terminals? Is the device healthy?Multimeter, LEDs, loop calibrator, eyes
NetworkCan the nodes reach each other? Is the bus terminated and biased?ping, switch port status, RS-485 checks, oscilloscope
ProtocolAre requests answered correctly? Right address, function, data type?Wireshark, Modbus poll tools, BACnet explorers, MQTT clients
ApplicationIs the logic, scaling, schedule, mode or override right?Controller tool, trend logs, BMS event log

Before you start

  1. Define the symptom precisely. "Room 2.14 is cold" becomes "room 2.14 reads 18.5 °C at 10:00 on weekdays, setpoint 21 °C".
  2. Ask what changed. Software update, new contractor, season change, DST change, power cut.
  3. Look at trends first. Five minutes of history often saves an hour on site. Did it ever work? When did it stop?
  4. Change one thing at a time and write down what you changed, so you can undo it.

Interactive: a troubleshooting tree

Half-splitting

When a signal passes through many stages, test in the middle. A temperature crosses sensor → cable → controller input → controller object → gateway → BMS server → graphic. If the controller tool shows the right value, the fault is on the right-hand half. One measurement removes half the suspects. With 7 stages, three measurements are enough to find the stage.

A Modbus RTU bus with 12 energy meters works for weeks, then meters 9–12 start timing out at random. The logs show CRC errors. Physical layer: a new meter was added at the far end and the 120 Ω terminator was moved to it, but the old terminator was left in place in the middle. Two mid-line terminators and a long stub created reflections. Fixing termination, not software, cleared it.
Do not "fix" a symptom in the application layer. Adding a +3 K offset to a sensor that reads low because it sits in a draught hides the real fault and confuses the next person. Fix the cause, or document the workaround clearly in the point list.

A BACnet controller value on the BMS has been frozen at 21.3 °C for two days. Ping to the controller works. What next?

  • Bottom up: physical → network → protocol → application.
  • Define the symptom, ask what changed, read trends before going on site.
  • Half-split long signal chains. Change one thing at a time.
  • Fix causes, not symptoms.

25.6 Working with contractors

Building automation sits between trades. The mechanical contractor installs valves, the electrician pulls cables, the panel builder wires cabinets, the controls integrator programs controllers, IT runs the network, and each equipment vendor owns its own controller. Most problems happen at the boundaries between them.

Define the interfaces

A responsibility matrix (often called a RACI or a division-of-works list) says who supplies, installs, wires, configures and tests each item. Write it before tendering, not after the first argument.

Splits vary by contract. These answers show a common arrangement.

Specifications that work

  • Sequences of operation written in testable language, with numbers: "If supply temperature < 5 °C for 10 s, stop fan, close outdoor damper, open heating valve 100 %, raise P1 alarm."
  • Naming convention and point list template provided by the owner, so every contractor uses the same.
  • Open interfaces required by contract: documented protocol, register maps, no per-point licence surprises.
  • Deliverables list with acceptance criteria and retention money tied to it.

Interactive: a handover checklist

A hotel retains 5 % of the controls contract until three conditions are met: all functional tests signed, seasonal cooling test done in July, and a restore of the BMS server from the handed-over backup performed by the hotel's own engineer. The restore failed the first time because a licence file was missing. That was found in week 2 of operation, not during a crisis three years later.
Watch for "soft lock-in": encrypted controller programs, admin accounts kept by the contractor, or tools only the original integrator can buy. Write into the contract that the owner receives full admin access, source programs and the right to use another integrator.

A chiller's Modbus values do not appear in the BMS. Controls says the chiller is wrong, the vendor says the BMS is wrong. What resolves it fastest?

  • Problems live at interfaces. Write a responsibility matrix early.
  • Specify testable sequences, a naming convention and open interfaces.
  • Tie retention money to handover deliverables, including a proven restore.
  • The owner MUST hold admin access, source programs and licences.
