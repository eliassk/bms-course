Chapter 07

Gateways and integration patterns

Real buildings never speak one protocol. A boiler talks Modbus, the lighting talks DALI or KNX, the chillers talk BACnet and the TVs talk a vendor's IP API. Integration is the craft of turning all of that into one consistent, trustworthy model. This chapter is about the software in the middle: gateways, mappings, update strategies and the failure handling that separates a demo from a system you can leave running for ten years.

7.1 Why gateways exist

A gateway is a device or program that sits between two protocol worlds and translates. On one side it speaks the field protocol of some equipment: Modbus RTU on RS-485, M-Bus, DALI, KNX TP, a proprietary serial link. On the other side it speaks something the supervisory layer understands: BACnet/IP, Modbus TCP, MQTT, OPC UA or a REST API.

Gateways exist for four reasons, and it helps to know which one you are solving.

ReasonWhat the gateway doesTypical example
Physical layerBridges media: RS-485 to Ethernet, M-Bus current loop to IP, DALI two-wire to IP.A Modbus RTU to Modbus TCP converter. Same protocol semantics, new transport.
Protocol semanticsConverts the data model: registers become BACnet objects, KNX group addresses become MQTT topics.A Modbus to BACnet gateway on a chiller.
AggregationPolls many slow devices locally and serves one fast, cached view upstream.One gateway reads 60 heat meters over M-Bus every 15 min and publishes the totals.
IsolationKeeps a fragile or insecure network segment away from the main LAN.A vendor's plant controller that must not be reachable from the office VLAN.

Physically, gateways come as small DIN-rail boxes (for example from Moxa, HMS Anybus, Intesis or Loytec, among many others), as a function built into a controller, or as pure software running on a server or a container. The software kind is increasingly common because one Linux host can run dozens of protocol drivers.

Explore: anatomy of a gateway

A school has 24 heat meters on one M-Bus segment. At 2400 baud a full readout of one meter takes roughly 1–2 seconds, so a sweep of all 24 takes close to a minute. If the BMS, an energy platform and a billing tool each polled the meters directly, they would collide on the bus. A gateway polls once every 15 minutes and serves all three from its cache.
Every gateway adds a place where data can be stale, mis-scaled or silently frozen. A gateway that keeps serving its last cached value after the field bus died is worse than one that reports "no data". Always ask how a gateway signals quality upstream (7.6).

A Modbus RTU device must be reached from a Modbus TCP client. No data model change is needed. What kind of gateway is this?

  • Gateways bridge media, data models, speed and security zones.
  • The internal point database with quality flags is the heart of every gateway.
  • Slow buses are read once and served many times from a cache.

7.2 Protocol translation and point mapping

Translation is mostly a big table. Each row says: read this thing here, interpret it like this, expose it there under this name. That table is called the point map or points list. On a mid-size building it has thousands of rows, and almost every integration bug is a wrong cell in it.

For each point you must decide:

ColumnQuestionExample
Source addressWhere is it?Slave 3, holding register 40107 (offset 106)
Data typeHow many bits, signed or not, integer or float?INT16, UINT32, FLOAT32
Byte / word orderFor 32-bit values, which register is the high word?ABCD (big-endian) vs CDAB (word swapped)
Scale and offsetRaw to engineering units.value = raw × 0.1 − 40
UnitWhat does the number mean?°C, kW, m³/h, %
AccessRead, write, or both? Command or setpoint?R for sensors, RW for setpoints
Target nameHow is it exposed northbound?BACnet AI:12 "AHU1 Supply Temp", or topic site/ahu1/supply_temp
Update rulePoll rate, COV increment, heartbeat.poll 10 s, publish on change ≥ 0.2 K

The trickiest columns are type and word order. Modbus registers are 16 bits. A 32-bit float spans two registers, and the Modbus standard does not say which comes first. Vendors differ. A float of 21.5 read with the wrong word order becomes a nonsense number like 2.6e-41 or a huge value. That is actually the lucky case: an obviously wrong number is caught at commissioning. The dangerous case is a value that is wrong but plausible, for example a missing ×0.1 scale that shows 215 °C as 21.5 °C on a different point.

Try it: point mapping builder

Naming is part of mapping

A point map with names like HR107 is useless upstream. Good maps use a consistent naming scheme or a tagging model. Project Haystack and Brick Schema are two open approaches that attach semantic tags (supply, air, temp, sensor) or typed relations to points, so software can find "all supply air temperatures" without parsing names. Even without them, a fixed pattern like site/system/equipment/point pays off quickly.

An energy meter exposes total active energy as UINT32 in Wh across registers 30073–30074, word order CDAB. The gateway reads both, swaps words, multiplies by 0.001 to get kWh and publishes site/meters/main/energy_kwh only when it changes by at least 0.1 kWh. One row of the point map captures all of that.
Modbus documentation mixes 0-based offsets and 1-based "register numbers" like 40001. Being off by one register gives you a neighbouring value that often looks plausible. Verify every new device against a known reading on site.

A FLOAT32 point shows 2.3e-41 instead of about 20. What is the most likely cause?

  • The point map is the integration. Treat it as versioned, reviewed source.
  • Type, word order and scale cause most mapping bugs.
  • Plausible wrong values are more dangerous than absurd ones.

7.3 Polling vs. push vs. subscription

Every integration must decide who starts the conversation when a value changes. There are three patterns.

PatternHow it worksExamplesStrengthWeakness
PollingClient asks on a timer.Modbus, SNMP GET, REST GET loopsSimple. Client controls load. Silence is detected automatically.Latency up to one interval. Traffic even when nothing changes.
PushDevice sends when something changes, to a configured target.KNX telegrams, webhooks, SNMP traps, syslogLow latency, low traffic.Lost messages are lost. Silence is ambiguous: quiet or dead?
SubscriptionClient registers interest; server then pushes changes for a time.BACnet COV, OPC UA monitored items, MQTT subscribe, WebSocket APIsPush latency with a managed relationship and often an initial value.State on both sides. Subscriptions expire and must be renewed after restarts.

The numbers matter. With polling, the average delay between a change and its detection is half the poll interval, and the worst case is a full interval plus the request time. A BACnet COV subscription has a lifetime (often set to minutes or hours). If the server reboots and forgets it, the client receives nothing until it re-subscribes. A robust client renews before expiry and also does an occasional full read.

Try it: load and latency simulator

Notice what the simulator shows. When values rarely change, push and subscription win by orders of magnitude on traffic. When values change constantly (power readings every second), push can generate more traffic than polling, which is why devices use a deadband or a minimum send interval. Polling also has a hidden benefit: a failed poll is an immediate health signal.

A BACnet supervisor integrates 400 VAV boxes with 8 points each. Polling every 5 s is 3200 property reads every 5 s. With ReadPropertyMultiple of 8 points per box it is 400 requests per 5 s, or 80 per second, still noticeable on an MS/TP trunk. Switching temperatures to COV with a 0.3 K increment drops steady-state traffic to a few messages per second.
Never rely on push alone for anything important. Pair it with a heartbeat or a slow background poll so that silence can be told apart from failure.

You poll every 30 s. A pump trips at a random moment. What is the average detection delay?

  • Polling: simple and self-checking, but slow and chatty.
  • Push: fast and light, but silence is ambiguous.
  • Subscriptions must be renewed and backed by an occasional full read.

7.4 Writing your own gateway (Node, Python)

When no off-the-shelf gateway fits, writing one is very achievable. Mature open-source libraries exist: for Node.js, modbus-serial, node-bacnet and mqtt; for Python, pymodbus, BAC0/bacpypes3, asyncua and paho-mqtt or aiomqtt. The protocol code is rarely the hard part. The hard part is everything around it.

The shape of a good gateway

A compact Node.js skeleton shows the structure. It is not production code, but every production gateway has these parts.

import ModbusRTU from "modbus-serial";
import mqtt from "mqtt";

const POINTS = [
  { reg: 106, type: "f32", scale: 1, topic: "site/ahu1/supply_temp", db: 0.2 },
  { reg: 110, type: "u16", scale: 0.1, topic: "site/ahu1/fan_speed", db: 1 },
];
const last = new Map();
const bus = new ModbusRTU();
const broker = mqtt.connect("mqtts://broker.local", {
  will: { topic: "site/gw1/status", payload: "offline", retain: true },
});
broker.on("connect", () => broker.publish("site/gw1/status", "online", { retain: true }));

async function cycle() {
  for (const p of POINTS) {
    try {
      const { buffer } = await bus.readHoldingRegisters(p.reg, p.type === "f32" ? 2 : 1);
      const raw = p.type === "f32" ? buffer.readFloatBE(0) : buffer.readUInt16BE(0);
      const v = raw * p.scale;
      // Publish on change beyond the deadband, or as a heartbeat.
      const prev = last.get(p.topic);
      if (!prev || Math.abs(v - prev.v) >= p.db || Date.now() - prev.t > 300_000) {
        broker.publish(p.topic, JSON.stringify({ v, ts: Date.now(), q: "good" }), { retain: true });
        last.set(p.topic, { v, t: Date.now() });
      }
    } catch (e) {
      broker.publish(p.topic, JSON.stringify({ v: null, ts: Date.now(), q: "bad" }), { retain: true });
    }
  }
  setTimeout(cycle, 10_000);
}
await bus.connectRTUBuffered("/dev/ttyUSB0", { baudRate: 9600 });
bus.setID(3); bus.setTimeout(500);
cycle();

What separates a hobby script from a gateway

ConcernDo this
ConfigurationPoint map in a file (YAML/JSON/CSV), validated at start. No addresses in code.
ConcurrencySerial buses are half-duplex. Serialise all requests on one bus through a single queue.
Block readsGroup contiguous registers into one request. 10 points in one read is ~10× faster than 10 reads.
QualityEvery value carries timestamp and quality. Never publish a stale value as fresh.
WritesValidate range and type, rate-limit, log who wrote what. Read back to confirm.
ReconnectBoth sides reconnect with backoff (7.6). A broker restart must not crash the process.
SupervisionRun under systemd, a container restart policy or a service manager. Expose health.
TestsUnit-test decoding and scaling with captured raw frames. That is where bugs hide.
A Python gateway built on asyncio runs one task per serial bus, each with its own request queue, plus one MQTT client task. A crash in the decoding of one point is caught, that point gets quality "bad", and the other 300 points keep flowing.
Two programs opening the same serial port, or two Modbus masters on one RS-485 bus, produce collisions and random CRC errors. One bus, one master, one queue.

Your gateway reads 40 registers on one RTU bus with 40 separate requests. What is the biggest, cheapest win?

  • Libraries handle protocols. You handle config, quality, writes and recovery.
  • Serialise access per bus. Batch contiguous reads.
  • Test decoding with real captured data.

7.5 Low-code integration: Node-RED

Node-RED is an open-source, flow-based tool that runs on Node.js. You build programs in a browser by wiring nodes together. Each node receives a message object, usually called msg, does one thing, and passes it on. The main data lives in msg.payload; the source often sets msg.topic.

It ships with nodes for MQTT, HTTP, TCP/UDP, files and timers. Community packages add Modbus, BACnet, OPC UA, KNX, SNMP and many vendor APIs. For integration work this is very productive: a working bridge from a REST API to MQTT can take ten minutes.

Step through a flow

A typical function node body is plain JavaScript:

const raw = msg.payload[0];          // register value
msg.payload = { v: raw / 10, unit: "°C", ts: Date.now() };
msg.topic = "site/boiler/flow_temp";
return msg;

Where it fits, where it hurts

Good forPainful for
Glue between APIs and MQTT; quick vendor integrations; prototypes; notifications; small sites.Thousands of points; complex state machines; code review and diffing (flows are big JSON files); strict testing.
A hotel integrates its booking system's webhook with room heating. An HTTP-in node receives "check-in room 214", a function node maps it to hotel/f2/room/214/mode/set = comfort, and an MQTT-out node publishes it. A second flow sets "eco" on checkout. The whole thing is six nodes.
Flows grow. A 300-node flow with logic buried in function nodes and global context variables is as hard to maintain as any spaghetti code. Keep flows in git, use subflows, keep function nodes short, and move heavy logic into a proper service.

In Node-RED, which property normally carries the main data between nodes?

  • Node-RED: messages flow through wired nodes; data lives in msg.payload.
  • Excellent glue and prototyping tool.
  • Version flows, handle errors with catch nodes, and keep logic small.

7.6 Stale data, reconnects, watchdogs

The most dangerous value in a BMS is a frozen one. A screen shows 21.3 °C, perfectly normal. But the sensor's gateway died two days ago and the number is simply the last thing received. Nobody notices until a room is cold. Robust integration makes staleness visible.

Three tools

ToolHow it worksTypical numbers
Timestamps + max ageEach value carries the time it was read. Consumers treat values older than a limit as stale.Max age = 3 × expected update interval.
HeartbeatThe source sends something periodically even if nothing changed: a counter, a "still alive" message, or a resend of the value.Every 30–300 s.
WatchdogA timer that is reset by every heartbeat. If it expires, the point or device goes to "unavailable" and an alarm can fire.Timeout = 2–3 heartbeats, so one lost message is tolerated.

Protocols help. MQTT has keepalive and the last-will message (Chapter 06). Modbus gives you timeouts per request. BACnet has a status flags property with a FAULT bit and a Reliability property. OPC UA attaches a StatusCode and timestamps to every value. Use them; do not reinvent them.

Try it: watchdog timeline

The trade-off is plain: a short timeout detects real failures fast but raises false "unavailable" states when a message or two is lost. A long timeout is calm but slow. Two and a half to three heartbeats is a common compromise.

Reconnect with exponential backoff

When a connection drops, a client must reconnect. Retrying immediately in a tight loop hammers the server, floods logs, and when 200 clients all do it after a broker restart, they can knock the server over again (a "thundering herd"). The standard fix is exponential backoff with jitter: wait 1 s, then 2, 4, 8… up to a cap such as 60 s, and randomise each wait so clients spread out. Reset the delay after a connection has stayed up for a while.

// Full jitter: random wait between 0 and the capped exponential delay.
const delay = (attempt) => Math.random() * Math.min(cap, base * 2 ** attempt);
A gateway publishes each point with {"v":21.3,"ts":…,"q":"good"} and a device heartbeat every 30 s. The front end greys out any tile whose value is older than 90 s and shows "unavailable" when the gateway's retained status topic says "offline" via its last will.
Retained MQTT messages and gateway caches make old values look current. A retained value from last week is delivered instantly to a new subscriber. Always carry a timestamp in the payload, or combine retained values with an availability topic.

Heartbeat every 20 s, 5 % random loss. Which watchdog timeout best balances speed and false alarms?

  • Every value needs a timestamp and quality. Frozen data is the silent killer.
  • Heartbeat + watchdog at 2.5–3 intervals turns silence into a clear state.
  • Reconnect with exponential backoff and jitter. Never in a tight loop.

7.7 Integrating vendor systems (AV, TVs, network gear)

Beyond HVAC, a modern building contains many systems that were never designed for a BMS: audio DSPs, projectors, displays, video matrices, network switches, UPS units, access control. Each comes with its own control interface, and their quality varies wildly.

Interface typeWhat it looks likeExamples
Serial command setASCII or hex strings over RS-232, often 9600 8N1. Frequently also available over raw TCP.Many projectors and displays; legacy matrix switchers.
Raw TCP / TelnetLine-based text protocol on a fixed port.PJLink (projectors, TCP 4352); many DSPs and matrix switchers.
HTTP / REST / JSON-RPCHTTP requests with JSON. Sometimes with tokens or digest auth.Many smart TVs, newer AV processors, cloud-connected devices.
WebSocketPersistent connection with pushed events.Some TV and AV platforms; modern conferencing systems.
SNMPMIB-based GET/SET, traps for events.Switches, UPS units, PDUs, printers.
Vendor cloud APIInternet REST API with OAuth.Consumer devices, some heat pumps and EV chargers.
CEC over HDMILow-level control over the HDMI cable.Power and input on consumer TVs, via a small adapter.

Patterns that work

  • One driver per device type, exposing a small, normalised model: power, input, volume, mute, online. The rest of the system never sees vendor commands.
  • Track state yourself when the device cannot report it. Many displays cannot be queried while powering on. Assume, then confirm when possible.
  • Respect timing. Projectors may ignore commands for 30–60 s during warm-up and cool-down. Queue commands and send them when the device is ready.
  • Prefer local over cloud. A cloud API adds internet dependency, rate limits and the risk that the vendor changes or retires it.
  • Separate network gear monitoring from control. Read port status, PoE power and errors via SNMP; leave configuration to network tools.

Sort the interfaces

Projector power via PJLink
UPS battery level from a network card
Smart TV input switching over the LAN
Switch port link status
Heat pump with only a vendor app
Audio DSP gain change via Telnet
A conference centre has 20 displays from two brands, 6 projectors and a DSP. Each device type gets a driver that publishes av/room3/display1/power, …/input and …/online. A "presentation" scene in the BMS sets lights to 40 %, lowers blinds, powers the projector and routes the lectern input. The scene logic does not care which brand the projector is.
Vendor APIs change with firmware updates. A TV that accepted a command last month may need a new pairing token after an update. Pin firmware where you can, monitor "online" per device, and keep the driver's version notes with the point map.

Why expose a normalised model (power, input, online) instead of raw vendor commands?

  • Vendor systems use serial text, HTTP, WebSocket, SNMP or cloud APIs.
  • Write one driver per type and expose a small normalised model.
  • Prefer local control; watch for firmware changes.
